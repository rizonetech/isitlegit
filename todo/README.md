# TODO system: format spec

The `todo/` tree is the live execution plan for building the project. Markdown is canonical; `build/todo-cache.json` is a derived, gitignored projection. The one committed derived artefact is [`implementation-plan.md`](./implementation-plan.md), generated from the sections and never edited by hand.

One rule governs everything below: **a TODO section must be implementable by someone with zero conversation context.** A fresh session starts with none. If a section only makes sense to someone who was in the room, it is not done.

This system is the one Rizonetech uses in Recto and its other repositories, installed from Rizonetech's Conclave-SDK (the `todo` and `reviewer` kits) on 2026-10-26: one validator that refuses malformed work, a generated plan, and stamps backed by review receipts. The governing product documents stay where they are: the design spec and tech stack in `docs/specs/`, the day plan in `docs/plans/`, the interface in `design/SPEC.md`. TODO files execute those documents; they do not restate them.

## Tree shape

```text
todo/
├── README.md               this file
├── TODO-00-INDEX.md        root index: domain order + active work
├── implementation-plan.md  generated by plan --sync; never edited by hand
├── plan.json               the plan's title, acceptance bar and phase names
├── findings.md             defects noticed while doing something else (file:line, unscheduled)
├── templates/              TODO-template.md (same file the create-todo skill carries)
├── 00-workspace/
│   ├── INDEX.md            domain index: every TODO in this domain
│   ├── TODO-01-<short-name>.md
│   └── TODO-02-<short-name>.md
└── 01-intake/
```

Domains are flat-numbered in allocation order: `00-workspace`, `01-intake`, `02-checks`, `03-vision`, `04-agent`, `05-trust`, `06-invoice`, `07-app`, `08-eval`, `09-launch`, `10-media` (the media lane's videos, uncoordinated), `99-manual` (operator only). Numbers are stable addresses: a new domain appends after the last one, because `DNN` cross-references encode them. Execution order lives in the dependency graph, not in the numbering.

Naming: `TODO-NN-short-name.md`, where `NN` is the next free number within that domain. Numbers are never reused. Renaming a file is safe: the stable `id` in frontmatter is what file-level references resolve against.

## Frontmatter

Every TODO file opens with YAML frontmatter, one scalar per line. Five required fields, four optional. That is the whole schema: resist adding more.

```yaml
---
schema_version: 1
id: example-runtime                # stable, kebab-case, globally unique, survives renames
domain: 01-intake                  # must match the containing directory
status: active                     # draft | active | blocked | done | superseded
title: "TODO-01 -- Example Runtime"
depends_on: ["repo-and-build"]     # optional: TODO ids that must fully ship first
frozen: true                       # optional: touches the safety contract in AGENTS.md
track: day-1                       # optional: build plan day
superseded_by: other-todo-id       # required with status: superseded
---
```

`id` rules: lowercase `a-z0-9-`, 2 to 60 chars, starts with a letter, no trailing dash. It must not change once other files point at it. Only `active` files produce ready sections. `done` is true exactly when every section is stamped (the last stamp sets it). A `superseded` file must name where its work went.

## File anatomy

In order: frontmatter, `# TODO-NN -- Title`, `> **Goal:**`, `> **Current state:**` (measured, dated, real paths), `## Inputs`, `## Outcome` (with the Adjacency line), `## Implementation Order`, the numbered sections `## 1.` to `## N.` in ascending order, and `## Verification` last. New sections go in numerical position, never after `## Verification`.

### The Implementation Order table is the dependency graph

Every `## N.` body section has exactly one row (`Order`, `§N`, `Deliverable`, `Depends On`, `[ ]`), and every row has exactly one body section. Keep every section heading (`## N. <Title>`) and its `Deliverable` cell (plus `Scope` cells in index tables) to a concise noun phrase of at most 88 characters so raw Markdown table rows stay under 140 characters (with description cells <= 88 characters) and never wrap in raw `.md` view; put file paths, symbol lists, and flags in the section body and checklist. The validator enforces both directions, refuses `Deliverable` or section titles over 88 characters, refuses cycles, refuses a prerequisite in a later phase than its consumer, and refuses a ticked row without its stamp. A file holds at most 55 sections: past that, the next work opens a new file in the same domain, split by subject. Section numbers are permanent addresses and are never renumbered.

### Cross-reference notation

| Form | Means | Example |
| ---- | ----- | ------- |
| `§N` | Section N of this same file | `§3` |
| `TNN §N` | TODO-NN in the same domain, section N | `T02 §1` |
| `DNN TNN §N` | Domain NN, TODO-NN, section N | `D03 T01 §4` |

Never a bare number, and never a cross-TODO reference without a section. Cross-references in `-> XREF:` lines are bidirectional at file level: if this file points at `D03 T01 §4`, that TODO file must point back at a section in this file. The validator refuses one-sided XREFs and XREFs that name no real section.

### What every section declares

- `**Phase:**` from the closed list: 0 to 7 or 99 (Manual, operator only). The phase drives plan ordering; changing one is a scope decision. The project names its phases, the plan's title and its acceptance bar in `todo/plan.json` (`{"title": ..., "acceptance": ... or null, "phases": {"0": "<name>", ...}}`); `validate` and `plan` refuse unknown keys or phase numbers.
- `**Needs:**` `none` or a comma-separated list from: `meta-api` (a Meta Model API key with the hackathon credit applied; every call costs money; reachable when `python3 scripts/check-meta-key.py` exits 0 (the vault's key, read through `conclave-op`, has Meta's shape and Meta accepts it on its free model list; the key is never printed; a placeholder, a revoked key or a stalled vault is not reachable) and `todo/99-manual/TODO-01-day0-accounts.md` has a `Meta credit visible: YYYY-MM-DD` line), `cloudflare` (Wrangler signed in to the Rizonetech Cloudflare account: `pnpm exec wrangler whoami` names it), `live-mail` (`isitlegit.co.za` routes mail to the Worker and SMTP2GO sends from it), `whatsapp` (the Meta app's WhatsApp test number and recipients), `attended`, `owner-decision`, `third-party`, `operator`. `owner-decision`, `third-party` and `operator` hold the section out of `query ready` until the answer is recorded and the Need is removed. Unattended runs never take an `attended` or `operator` section.
- `**Risk:**` `full` or `light`, optional, `full` when absent (D00 T01 §15). The following round schedule applies to historical round-based policies; current Codex two-pass chains use their combined schedule instead. A `light` section's rounds run `[schedule.light]` in `.conclave/reviewers.toml` (cheaper fixed rounds; the stop rule and escalation unchanged, so a P1 or P2 still earns another round). `light` is allowed only when every path the section names in backticks is tooling, tests or docs (`scripts/`, `tests/`, `test/`, `docs/`, `todo/`, `.claude/`, `.github/`, `design/`) and none names a guarded word (auth, mail, meta, secret, credential, redact, leak, migration, sample, trust, bank, payment); `scripts/review-dispatch.py` reads it from the section the findings file names, and the stamp replays each round on the schedule it ran on. Changing a section's risk starts its rounds again from round 1, earlier findings kept. A switch kept for when time runs out (operator, 2026-10-31), `LIGHT_INCLUDES_PAGES` in `scripts/lib/todo_graph.py`, off: turned on, it also lets member-facing pages (`src/web/`) and the eval (`eval/`) be light, while pages that sign people in, sign links, take uploads or decide access, and every other `src/` place, stay full.
- `**Surface:**` `yes` or `no`. A `yes` section builds or changes a user-facing surface and also carries four lines: `**Fidelity:**`, `**Job:**`, `**Treatment:**`, and `**Chrome:**`.
- `**Freeze check:**` in every section of a `frozen: true` file, and nowhere else.
- `**Build order:**` numbered steps, each naming a path, class, command or artifact in backticks and an observable `Done when:`.
- A checklist of 1 to 30 micro-step items, `- [ ] Commit: <message>` last. One item is one buildable step: one action, a named path or symbol in backticks, a `Done when:` observable end state in the same bullet, a `Cheaper substitute:` on UI and write items, and a source citation when behavior is copied from the SPEC, the design spec, or upstream specifications.
- `**Test checkpoint:**` a runnable command in backticks with its expected result. It must be able to fail.

Do not rewrite a `[x]` section's checklist: that is the contract its stamp covers. New granularity on shipped work is a new section.

### Micro/small items and 100% complete development plan

- **Small, single-responsibility sections:** Never bundle multiple subsystems, dialogs, or workflows into one coarse umbrella section. Split work into small, single-responsibility sections that each deliver one coherent capability, with explicit `Depends On` edges in the Implementation Order table.
- **Short table descriptions (`<= 88` chars):** Every `Deliverable` cell and `## N. <Title>` heading is a short noun phrase (`<= 88` chars, enforced by `validate`) so raw `.md` table rows in `TODO-*.md` and `todo/implementation-plan.md` never wrap in the editor.
- **Granular micro-step checklist items (five-part rule):** Never write a 1-bullet or 2-bullet summary checkbox for an entire subsystem. Decompose every section into individual micro-step checkboxes (typically 4 to 15 micro-steps per section, max 30). Every non-`Commit:` item carries: (1) one action (never "do X and then Y"), (2) a concrete path, symbol, or command in backticks, (3) `Done when:` observable end state in the same bullet, (4) `Cheaper substitute:` on UI and write items so the checkpoint and reviewer fail on shortcuts or wrong-layer edits, and (5) a source citation when copying behavior.
- **100% complete development plan:** Running `process-plan` to completion must leave a 100% complete, shippable product. Every commitment in the design spec and build plan and every screen, dialog, control, command, setting, error/refusal path, undo/reverse operation, and persistence read-back in `design/SPEC.md` is owned by a concrete section and micro-step. Never cap operator-requested planning and never silently drop scope.
- **Surface completeness (`Surface: yes`):** Every control, menu item, dialog, and state on the SPEC surface is either working (proven on the rendered surface with real data and read-back) or deferred to a named, resolving section (`-> XREF: DNN TNN §N`). A disabled or stubbed control with no resolving owner section refuses validation and review.
- **Logical step commits:** Commits follow logical steps within a section; a section may land in one or more step commits, and review fix-loop commits append to the candidate range without amending.

### Brownfield code and incomplete TODO trees

When adopting or grooming this system on a repository where code is already partially implemented or the `todo/` tree is incomplete:

- **Already-stamped `[x]` sections are never rewritten:** Their checklist is the historical contract covered by their receipt. If a `[x]` section was coarse or left gaps, keep it untouched and file the missing work as a new `## N.` section in numerical order with `-> XREF:` back to the original section. If a `[x]` section's `Test checkpoint` no longer passes, `review-todo-section` in audit stance flips it back to `[ ]` with a dated regression note.
- **Open `[ ]` micro-steps already implemented in code:** During `groom-plan` or `process-todo-section` Step 2/3, verify the existing code against the micro-step's `Done when:` and `Cheaper substitute:`. If 100% satisfied, tick `[x]` with the `file:line` and commit SHA that shipped it. If only partially implemented (for example, happy path exists but refusal path, token binding, or test is missing), leave it `[ ]`, update `> **Current state:**` to name what exists, and decompose the remaining work into concrete micro-steps.
- **Open `[ ]` section already 100% implemented in code:** Do not churn working code just to manufacture a diff. Verify every micro-step's `Done when:`, add any missing falsifiable test if the checkpoint cannot fail, run the `Test checkpoint` for real, commit the ticked checklist and verification evidence, and run `review-todo-section` plus `stamp` against the implementing or verification commit SHA.
- **Features already in the codebase with no TODO file:** Features that are already 100% complete and tested in the baseline codebase are recorded in `> **Current state:**` of the relevant domain's TODO file; features that are incomplete, untested, or stubbed get small single-responsibility sections and five-part micro-steps for the remaining work so (`baseline code` + `open plan`) equals a 100% complete product.

### Adjacency: the surfaces a file owes beyond its record

`## Outcome` carries one executable `**Adjacency:**` line. Write every key exactly once, separated by semicolons: `key=applicable`, `key=applicable @ DNN TNN §N` for an explicit owner, or `key=not-applicable (reason)`. A narrow non-feature file may declare `all=not-applicable (reason)`. The nine keys: `list` (find a record without its identifier), `document` (what a user carries, sends, prints or files), `settings` (every tunable, with a named consumer), `reporting` (summaries and exports over the domain's data), `notifications` (lifecycle notices with recipient rules), `permissions` (refusals exercised, both ways), `audit` (who changed what, and the diagnostic trail), `exchange` (import and export), `reverse` (the undo of every create: cancel, reopen, revert). "Not applicable" is a declaration with a reason, not silence. Owner references must resolve; `python scripts/todo-graph.py query adjacency` prints every declaration. An `**Adjacency rationale:**` paragraph under the line records the substantive decisions for human review.

## Stamps and receipts

A section closes only through `stamp`. This example uses the current Codex two-pass policy; a historical chain supplies its actual required review arguments:

```powershell
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <full 40-char implementation commit> --plan 'docs/reviews/01-intake/D01-T01-s1.md' --completion 'docs/reviews/01-intake/D01-T01-s1.md:complete' --check '<command> -> <quoted result>'
```

The section's plan review (`--plan`) must have read the contract before the build: its candidate is the commit that records the section's `> **Started:**` line or an earlier one, or a later commit only when the section has an explicit `Started:` line and, every commit that descends from the Started commit and leads to the candidate (a branch forked after it included) changes only `todo/` and `docs/reviews/`, or reformats an existing JSON file under `test/` or `tests/` to the same parsed value, and leaves the section's contract (its text and its TODO file's preamble, its own Implementation Order row found by its `§N` column) byte for byte as it was; the receipt records that evidence as `plan.after_started` and validation rebuilds it, and refuses it missing when the candidate follows the Started commit (D00 T01 §28).

### Codex two-pass and reconciliation receipts (4 November 2026, REVIEW-18)

The committed pin's `self_review_policy = "codex-two-pass-v1"` selects two normal reviews for Codex: a sound-plan self-review, then one combined quality and completion self-review after implementation and tests. The combined pass proves every agreed requirement completed and correctly implemented, with adversarial, integration, source-defect, plan-delivery, consistency, record, quality and optimization checks plus design for an actual `Surface: yes` section. No separate normal round or final review is required or permitted. The receipt contains the actual plan and exact complete combined review, `reviews = []`, `round_cap = 0` and `rounds_spent = 0`; those values do not authorize arbitrary empty review chains.

Historical three-pass receipts retain their original pins and actual rounds. A genuine legacy plan may transition explicitly with `--transition-plan` on the combined completion call only when there are no round or completion attempts and the committed pin enables `plan_transition = ["codex-self-review"]`. Its original prefix, digest, candidate and pin remain bound and the plan-before-build gate still applies. Do not erase attempts, relabel the plan or manufacture a round. Known-outage retries retain the transition identity.

Normal combined completion persists pending-call/result state in `build/review-completion/`. If a returned response could not be written to findings, recover it with `python3 scripts/review-dispatch.py --recover-completion --record <findings-path>` without invoking the reviewer again. An unresolved call or failed response persistence stays blocked; preserve the marker and report it. Only a known non-returned outage may retry. Both `--list-rounds` formats expose pending and recorded state.

Genuine additional suggestions outside approved obligations are recorded separately with an owner and disposition. Unmet requirements, safety breaches, real in-scope defects and regressions still block completion. A valid two-pass or historical three-pass chain ending `COMPLETION: gaps` can use D00 T01 §35's one explicit reconciliation when its committed pin authorizes it. Preserve the original chain and failed completion. A committed disposition addresses every original finding against unchanged approved requirements; the reviewer verifies the evidence and full intervening diff on the same or a descendant candidate. Only a real `RECONCILIATION: complete` supports this two-pass command:

```bash
python3 scripts/todo-graph.py stamp 'DNN TNN §N' --sha <verified-sha> --plan <findings-path> --completion '<findings-path>:gaps' --reconciliation '<findings-path>:complete' --check '<quoted checkpoint and command> -> <observed result>'
```

The new route has no `--review`. A historical three-pass chain additionally supplies its actual original round, `clean` if it found nothing or `fixed` only when verified repairs resolve it. The receipt retains `completion.verdict = "gaps"` and adds a separate `reconciliation` record. Validation replays exact candidate, original findings/completion binding, unchanged contract, committed disposition, authorized pin and chronology. Missing, altered, stale, unrelated or still-gaps evidence refuses. Old receipts are never rewritten and old gaps are not accepted automatically.

One returned reconciliation exhausts the bounded exception. A gaps verdict remains blocked pending an explicit coordinator decision. Its separate journal in `build/review-reconciliation/` supports `python3 scripts/review-dispatch.py --recover-reconciliation --record <findings-path>` to record the same persisted result without a new reviewer call. Unresolved calls stay blocked; known non-returned outages may retry. Full dispatch commands are in `docs/todo-workflow.md` and `.agents/skills/codex-lane-workflow/SKILL.md`.

Policy rollback changes authorization for new work in a new committed pin while preserving historical pins, findings, transition bindings, dispositions, pending state and receipts. It never deletes a returned review or converts failure into approval.

## Commands

```powershell
python scripts/todo-graph.py validate            # structure + graph integrity; exits 2 with the reason on any fault
python scripts/todo-graph.py build               # parse todo/ -> build/todo-cache.json
python scripts/todo-graph.py render              # mermaid dependency graph
python scripts/todo-graph.py plan --sync         # regenerate todo/implementation-plan.md after any edit
python scripts/todo-graph.py plan --check        # fail if the generated plan is stale (CI runs this)
git config merge.todo-plan.driver true          # once per clone: merges regenerate the plan, never conflict on it
scripts/merge-lane.sh <ref>                     # the way to merge a lane: one command through the §22 plan stop (D00 T01 §23)
                                                # on a conflict or hook refusal it leaves git's message and the open merge:
                                                # resolve and stage (or repair the refusal), then the commit below, or abort
git commit --no-edit                            # concludes a merge that stopped with 'regenerate the plan' (D00 T01 §22)
git merge --abort                               # backs out of such a stopped merge instead
python scripts/todo-graph.py query ready         # sections that can run now (also: blocked, stats, deferred, adjacency, plan)
python scripts/todo-graph.py resolve 'D01 T01 §1'  # 0 ready, 1 no such section, 2 no reference, 3 verified, 4 waiting
python scripts/todo-graph.py classify 'D01 T01 §1' 'D02 T01 §1'   # dispositions as JSON
python scripts/todo-graph.py stamp 'D01 T01 §1' --sha <commit> --plan '<report>' --completion '<report>:complete' --check '<cmd> -> <result>'
python -m unittest tests.scripts.test_todo_graph   # the tooling's own tests
```

## Rules for every file

- One line per paragraph and per list item in Markdown prose; no em dashes or en dashes in new text; keep Markdown table description cells at or under 88 characters so they do not wrap in raw `.md` view.
- A defect noticed outside the current work is filed in `todo/findings.md` with `file:line`, not fixed on the side inside someone else's commit; scheduling it means writing a section through `add-todo`.
- Questions that need a person are not TODO rows without a Need: the section names `owner-decision` or `third-party` and records the answer before the Need is removed.

### Exact exception receipts (D00 T01 §38)

Version 3 is an explicit exception binding inside the separate `reconciliation` receipt record, beside the unchanged original completion gaps. It adds the authorization document path, commit and Git blob, exact exception kind and accepted contract hash while retaining all original candidate, contract, prefix and disposition fields. It is permitted only for the two report/kind pairs documented in `docs/todo-workflow.md`, following a separate coordinator decision and committed pin entry. No live authorization is installed by the capability itself.

Receipt replay verifies the original chain, every preceding failed reconciliation, exact full prefix, committed authorization and disposition, candidate ancestry, contract hashes, recorded reviewer pin, schedule and chronology. A successful predecessor, missing/reordered/extra evidence, changed obligation, returned exception gaps or repeated exception cannot stamp. Historical versions 1 and 2 retain their existing rules and receipts. Revocation removes new-call authorization only and preserves all historical documents and pins.
