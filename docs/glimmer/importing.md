# Importing a public page dataset into Loupe's store

How the operator takes a downloaded dataset to a reconciled import (D03 T04 §5 and §18). Every command runs from the repository root; the store is `~/isitlegit-data/glimmer` (`GLIMMER_DATA_DIR` moves it) and never sits inside a git work tree. Run one import at a time: each renders pages in a headless browser.

## 1. Verify the download

Each source's files sit under `<store>/raw/<source>/` with their SHA-256 (or the publisher's own checksum) recorded where they were fetched: Astra's `COLLECTED.md` for a source it collected, `docs/glimmer/sources.md` for one fetched by hand. Re-check every file against it before anything else; a mismatch removes the source. Re-read the licence at the dataset's own page and record the decision as a row of `docs/glimmer/sources.md`, and an accepted source in `NOTICE.md`.

## 2. Turn the archive into rows or files

| Source | Command |
| ------ | ------- |
| ScamFerret | `python3 -I scripts/glimmer/scamferret_rows.py` (reads the archive `<store>/raw/scamferret/artifact-8cf8dc631edafe584141e2f95f0c0f51855fb7bc.tar.gz` entry by entry, never unpacked, once `INPUTS.json` binds it, and writes `rows.jsonl`, `EXPORT.json`, `ITEMS.jsonl` and `ITEMS.inventory.jsonl`) |
| PhreshPhish | `~/.venvs/fireworks/bin/python scripts/glimmer/phreshphish_rows.py` |
| CompPhish, Ariyadasa 2021, Kempf HTML, Look For Mallory | `~/.venvs/fireworks/bin/python -I scripts/glimmer/dataset_rows.py <source> [--max 15000]` |
| 7 Days Later | `~/.venvs/fireworks/bin/python -I scripts/glimmer/sevendays_rows.py [--max 15000]` |
| OWS, PhishingEval-Ji, PhishDecloaker, ARES 2021, Putra | `~/.venvs/fireworks/bin/python -I scripts/glimmer/new_rows.py <source> [--max 30000]` |

Archives are read entry by entry, never run; each entry, decompressed total, single-buffer allocation, retained-memory footprint (including lineage bookkeeping and ledger serialization), pending-part count and wall-clock deadline is bounded by `scripts/glimmer/inputs.py` (`Limits`). Every Hugging Face pin in `INPUTS.json` must name an immutable 40-digit commit hash, never a mutable branch or tag (`main`, `master`, `refs/...`). Each command first removes the staging a killed earlier run left (`scripts/glimmer/staging.py`) and writes `rows.jsonl`, `EXPORT.json`, `ITEMS.jsonl` and `ITEMS.inventory.jsonl` temp-then-rename with read-back verification.

## 3. Import

| Source | Command |
| ------ | ------- |
| ScamFerret | `node scripts/glimmer/import-scamferret.ts [--concurrency 4]` (reads only the rows its `EXPORT.json` names; rows without a receipt, or changed since, are refused) |
| PhreshPhish | `node scripts/glimmer/import-phreshphish.ts [--concurrency 4]` |
| CompPhish, Ariyadasa 2021, Kempf HTML, Look For Mallory, 7 Days Later | `node scripts/glimmer/import-rows.ts <source> [--concurrency 4]` |
| OWS, PhishingEval-Ji, PhishDecloaker, ARES 2021, Putra | `node scripts/glimmer/import-new.ts <source> [--concurrency 4]` |

The import writes `<store>/raw/<source>/IMPORT.json` as `running` before it touches a page, and at the end as `complete` or `incomplete` with every item accounted for: imported, a duplicate of a stored page, skipped (already stored from an earlier run, not rendered again), filtered (`captureProblem()` in `scripts/glimmer/label-rules.ts`: a CAPTCHA, consent or challenge wall in the DOM or title/text, a 404/error page, a directory listing or suspended host, a parked domain, or a blank page with neither visible text nor login/payment form fields, while a sparse lure with a logo and login or payment fields is admitted) or excluded (with its reason). More than 15 percent excluded, or a stop on a write failure, reads `incomplete`; an import only publishes `complete` to `IMPORT.json` after `<store>/raw/<source>/ITEMS.import.jsonl` is written and read back whole, bound to `{ inputs, rows, export, import }` with every item's `input` digest. A source is trained on and evaluated only once its import reads `complete`. A stopped or killed import is resumed by running the same command again.

## 4. Check, inspect, recover and reverse

- `node scripts/glimmer/sources.ts check` reconciles `docs/glimmer/sources.md`, every accepted source's `INPUTS.json`, `EXPORT.json`, `ITEMS.inventory.jsonl`, `ITEMS.jsonl`, `IMPORT.json` and `ITEMS.import.jsonl`, and every stored page's `item`, `items` (with per-item `input` digest and `lure` label), `input` digest and `evidence` (`title`, `overlays` and structural wall flags), and prints `sources: reconciled`.
- `node scripts/glimmer/sources.ts migrate-lineage` populates `ITEMS.inventory.jsonl`, `ITEMS.jsonl`, `ITEMS.import.jsonl` and stored-page lineage (`item`, `input`, `items`, `evidence`) for imports written before §28, recovering capture evidence and per-item lure labels from the bound rows and refusing any source whose inputs, export or pages disagree by generation or content.
- `node scripts/glimmer/sources.ts status` lists each source's pages and its import's status, counts and rate.
- `node scripts/glimmer/sources.ts remove <source>` takes a source's pages out of the store, removes `raw/<source>/ITEMS.import.jsonl`, and marks its `IMPORT.json` as removed; a rejected source must have no page left.
- **Recovery from refusals:**
  - *Converter limit or pin refusal* (`more than ... archive entries`, `more than ... bytes expanded`, `more than ... bytes retained at once`, `passes the ... byte allocation limit`, `the conversion passed ... seconds`, or a mutable Hugging Face commit pin): replace any mutable Hugging Face branch/tag in `raw/<source>/INPUTS.json` with the exact 40-hex commit SHA, verify the archive digests in `INPUTS.json` (`inputs.verify()`), and re-run the source's converter command in §2.
  - *Inventory or ledger disagreement* (`ITEMS.jsonl does not match the converter's input inventory`, `ITEMS.inventory.jsonl` missing/mismatched, or `ITEMS.import.jsonl` missing/mismatched): re-run the source's converter command in §2 to rewrite `rows.jsonl`, `EXPORT.json`, `ITEMS.jsonl` and `ITEMS.inventory.jsonl` from the verified inputs, then re-run the source's import command in §3 so `ITEMS.import.jsonl` and `IMPORT.json` are rewritten in lockstep.
  - *Generation or content mismatch* (`EXPORT.json was made from other inputs than INPUTS.json names`, `the import was made from other rows than EXPORT.json names`, `ITEMS.import.jsonl is not bound to its IMPORT.json`, or `migrate-lineage` refusing an unmatched item or changed generation): never edit a receipt or ledger digest by hand; re-run the converter in §2 when `INPUTS.json` changed, then re-run the importer in §3 so changed items are re-rendered, shared pages narrowed or replaced, and stale items removed.

## 5. The sample import's environments: install, verify and recover

The pilot client's sample import (`node scripts/glimmer/import-samples.ts import`, then `leak-check`) runs two Python environments outside the project's own: the entity pass (`scripts/glimmer/entities.py`, spaCy's `en_core_web_lg`, also Presidio for the redaction benchmark) in `~/.venvs/presidio`, and the OCR engine (`scripts/glimmer/ocr_text.py`, RapidOCR) in `~/.venvs/ocr`. Both are pinned package for package in `scripts/glimmer/requirements-entities.txt` and `scripts/glimmer/requirements-ocr.txt`, read from the working environments with `pip freeze` on 2026-10-31 (Python 3.14.4). To build either on a new machine, or to replace a damaged one, remove the folder and run:

```bash
python3.14 -m venv ~/.venvs/presidio
~/.venvs/presidio/bin/pip install --no-deps -r scripts/glimmer/requirements-entities.txt
python3.14 -m venv ~/.venvs/ocr
~/.venvs/ocr/bin/pip install --no-deps -r scripts/glimmer/requirements-ocr.txt
```

`--no-deps` installs exactly the listed versions and nothing newer. The model wheel is listed by its release URL with its SHA-256 (`en_core_web_lg-3.8.0`, `293e9547…29ab63`), and pip refuses a download whose hash differs.

Then check the installed model against the digest the redaction is pinned to (`ENTITY_MODEL.sha256` in `scripts/glimmer/redact.ts`, `2c670c29386ea89708bf55e443eb92ab40c9bd05efa94f53703e4db3505c3011`): the SHA-256 over every file of the model package, path and bytes in path order.

```bash
~/.venvs/presidio/bin/python -I -c "import sys; sys.path.insert(0, 'scripts/glimmer'); import entities; print(entities.model_digest(entities.MODEL))"
```

The printed digest must equal the pinned one. Until it does, `entities.py` refuses to start (`the model is not the pinned one`, or `the model is not installed`), every sample page is refused by the import, and the leak check fails; nothing is redacted by a model other than the measured one. Never change the pinned digest to match a new install: a new model is a new redaction, which the benchmark (`node scripts/glimmer/redaction-benchmark.ts`, every pipeline, exit status 0) must measure first, and which remakes every sample page (`redactionKey()`). Check the OCR engine with `python3 -B -m unittest tests.scripts.test_ocr_text` and a run of the leak check.

Both scripts also check their environment against its requirements file at start (`scripts/glimmer/pins.py`): an installed package at another version than its pin, or missing, refuses to start with a reason that names the package and both versions (`the environment does not match requirements-entities.txt (spacy is 3.9.0, pinned 3.8.18)`, and the same for `requirements-ocr.txt`), so an upgraded environment never runs under the old audit. Rebuild it as above rather than edit the pin: both requirements files are part of the redaction's key (`redactionKey()`), so a changed pin is a new redaction that remakes every sample page and needs the benchmark and a new leak check.

Beside the entity pass, rules that need no model find what the model reads past (D03 T04 §19, completion review gap 3): street addresses (a house number, capitalised words and a street type, or an Afrikaans `-straat` word, with the suburb, town and code after it), post boxes and private bags, South African towns, a postal code beside a town or a replaced place, and a name of two or more words signed under a closing (`Kind regards, …`, a business's sign-off such as `Customer Care` or `Standard Bank` kept). `redact()` in `scripts/glimmer/redact.ts` replaces each in the HTML, and admission and the leak check refuse a render, page text or screenshot that still shows one (`discoveredDetail()`, reported as `it shows a street address` and the like). A name in running text, or a lone first name, is still the model's alone; `docs/glimmer/redaction-benchmark.json` records what each layer removes, and `taskset -c 0-3 node scripts/glimmer/redaction-benchmark.ts --speed` writes the pass's speed beside Presidio's to `docs/glimmer/redaction-speed.json`.

When the leak check fails, its output names each failed page by its opaque id, the representation that failed (`text`, `record` or `OCR`) and the kind of failure, never the content, and ends with the command to run again: the import then the leak check when a page still names someone, the leak check alone when an environment could not read (rebuild it as above first).

## Resumable downloads

Every dataset file is downloaded with `scripts/glimmer/fetch.py` (D03 T04 §16), which `scripts/astra-collect.py` places as `.fetch.py` in the store's `raw/` before each collection, so both collection briefs call it by that name. It resumes an interrupted file with a validated range request, starts again when the server's file has changed or its ranges do not add up, and moves a file into place only when its published SHA-256 (or MD5) matches; a dataset that publishes no digest is not fetched, and the collector records it in `REJECTED.md`. Measured 2026-10-29 on a local 10 MB file whose first transfer dropped at 90 percent (after D03 T04 §16's reviews): `fetch.py` refetched 1,048,576 bytes (the last 10 percent) in the same run and verified the whole file against its published SHA-256, in 1.12 seconds, 1.0 of them its backoff before trying again; `curl --continue-at -` refetched the same 1,048,576 bytes in 0.07 seconds, but only when run a second time, with no digest check, and it appends to a file the server has changed since, where `fetch.py` starts again. Recovery: one run against two; integrity: verified against unverified; refetched bytes: equal. aria2c, the stronger comparator, is not installed on this host; its measurement is D03 T04 §20's.

### Segmented downloads

Decision (D03 T04 §20, 2026-10-29): `fetch.py` downloads a large file in up to four ranges at once, because the measurement said it earns its build. `scripts/glimmer/fetch_bench.py` served a seeded 96 MiB file capped at 8 MiB a second per connection, as a dataset host caps one connection, and dropped each run's first transfer at half its length; five runs each, medians, recorded in `docs/glimmer/fetch-bench.json`: `fetch.py` on one stream 12.5 seconds, aria2c 1.37.0 on one connection 12.24 seconds, aria2c on four connections (`-x4 -s4 -k1M`) 3.31 seconds. Four connections took 74 percent less time than one, past the 30 percent the plan set as the bar. All three recovered and verified the file in all five runs, and each sent only the half the drop had left (aria2c four-connection 65,536 bytes more). Reversal: `--segments 1` restores one stream for a run; removing the segmented path is one function in `fetch.py`. After the build (measured 2026-10-29T05:40:57Z at `d77e67a`, after §20's reviews, five runs each, medians, `docs/glimmer/fetch-bench.json`), with every run of every tool actually cut: the cut falls once an eighth of the file has been sent on the first transfer, the same byte for every tool. An earlier record set the cut at half of what the first transfer asked for, which a piece ending exactly there never reached and aria2c's first connection (which reads only its quarter) never met, so it measured no recovery; §20's completion review caught it (G9), and the acceptance line now requires every run cut. Cut once: `fetch.py` on four segments 3.41 seconds against aria2c's 3.15 on four connections (1.083 times, inside the 10 percent bar); first URL answering every request `503`, a mirror serving the file: 5.24 against 6.22 (0.84 times). Both refetched 0 bytes; every run of both tools recovered, was cut and verified. Honest limits: the host was loaded (load average about 11, imports running), the margin after a cut is under 9 percent, and this is one local server with a fixed per-connection cap; beating aria2c outright, several mirrors at once and a gigabyte HTTPS measurement are D03 T04 §21's. What closed the gap from the first post-build run (3.95 against 3.41; 13.75 against 6.46): a connection cut after bytes arrived is tried again at once, a free connection takes half of a slow range's rest, a failing first URL's `HEAD` no longer stops a mirror's file from coming in segments, and the digest is read back in file order as the leading ranges fill, so no whole-file pass follows the transfer.

How it works: a fresh download's first request is its first range (`GET Range: bytes=0-(N-1)`, N a quarter of the threshold and at least 128 KiB), as aria2c's is (D03 T04 §23). A valid `206` from byte 0 that gives the total length in `Content-Range`, a strong validator and no content coding answers for the `HEAD`, which is then not sent, and its bytes are kept as the file's first bytes. The `HEAD` is asked, once the first range has answered, only where that answer cannot answer for it: a `200` (the range ignored), a `206` with no strong validator or no total, another answer, or a failure (one asked to wait with `Retry-After` is waited out first, unless another source answered); a refused redirect rules the URL out with no `HEAD`. A file of at least `--segment-threshold` bytes (64 MiB by default) whose answer (the `206`, or the `HEAD`) gives its length, ranges (`Accept-Ranges: bytes`, or the `206` itself), no content coding and a strong validator is fetched in up to four ranges (`--segments N`, 0 for automatic, 1 for one stream). Each range is written at its offset in the partial file and its progress kept in the state file every MiB, by a thread of its own (flushed first, so the state never claims an unflushed byte), so a fresh process resumes each range where it stopped and fetches only what is missing. Every range shares the one failure budget, the per-source lock and limit, and the free-space floor checked before each write; each connection keeps its own rate floor. A range answer that does not fit the file (its offset, end, length, coding or validator) starts the file again on one stream; a shorter valid answer is continued. A state whose ranges do not tile the file, or whose partial file is the wrong length, starts the file again. The file is published only when every range is whole, the data flushed and the whole file's published digest matches; anything else keeps the partial for a rerun (or removes it, on a digest mismatch).

### Where the time goes after a cut

Measured 2026-10-29 for D03 T04 §21, on the bench's 96 MiB file over HTTPS with 20 ms added before every answer, cut once an eighth of the file had been sent, four ranges, five in-process runs (medians) and a stage trace of three more. Before the change below: Python's start-up and imports 0.12 seconds (bare Python 0.02; `http.client`, argparse with the colour module it always loads, `email.utils` and `ssl` most of the rest); the `HEAD` 0.05; the four ranges' requests to their headers about 0.03 each, side by side; state writes 0.01 in all; the digest's tail none worth counting (SHA-256 runs at about 0.08 seconds per 72 MiB here, and the hasher keeps up as the leading ranges fill); the cut range's retry about 0.03. The largest cost was none of these: the transfer ended 0.2 seconds after its last range was complete, because an idle connection looked for work only every 0.25 seconds and the hasher every 0.05, so a finished run waited out a sleep. Both now wait on one condition, rung when a range ends, a connection finishes or the run stops (`d9383a6`): the stage trace went from 3.33 to 3.37 seconds to 3.17 to 3.20. What remains against aria2c, a C program that starts in about 0.01 seconds, is mostly Python's start-up and the `HEAD`'s round trip, which aria2c folds into its first `GET`.

### Mirrors

`--mirror URL` (repeatable) names another URL for the same file (D03 T04 §22). The first `--url` and then each mirror are held to the same address, scheme and redirect rules.

Sources used together: on a segmented run, every live URL whose answer gives the same length and the same strong validator as the first to answer serves ranges together (the first URL's answer is its first range's `206` where that answers for its `HEAD`; each mirror is asked a `HEAD` beside the first range, as before, so no mirror's bytes are fetched before it is known to agree), spread round-robin over them, at most four connections in all. Two hosts that each cap a connection therefore give the file both hosts' bandwidth, where one URL at a time gave it one host's. Each range keeps its source; a free connection takes half of the slowest range's rest from the fastest source, moving that range's end in one step so the slow connection stops at the new end and the taken tail starts at once. A URL that gives another length or validator is logged and kept out of that mix, but stays in the ordered fallback.

Failover between them: a counted failure (a disconnect, a timeout, the rate floor, a `429` or `5xx`) is charged to the one `--attempts` budget whichever source it came from, and the failed source's unfinished ranges go to the others at once; a `Retry-After` pauses only the source that sent it. A refused route, a `404` or an answer that does not fit rules that source out of the mix while the others write on. A source whose validator or length changes mid-run is dropped, every range it wrote is fetched again (the cut is saved before any replacement byte is written), and the in-order digest is rebuilt over the replacements. When every source in the mix is ruled out, the file starts again, whole, from the next URL under its own representation. On a single stream (a file under the threshold, or `--segments 1`) the URLs are tried in order: a partial resumes on the next URL when its validator is the same, and starts again when it differs.

A file whose digest does not match: bytes from one URL alone rule that URL out and the next starts the file again. Bytes from several URLs cannot be blamed on one, so each source that agreed on the file is downloaded whole on its own into a file of its own and checked against the published digest. The one that verifies is published and each one that does not is ruled out; the search, and the sources ruled out, are saved in the state, so a fresh process goes on from there and never asks a ruled-out source again. A state written before the source of each byte was kept starts the search too. When every URL is ruled out, or the budget is spent, the run fails with the last reason and nothing is published.

The JSON line's `urls` names every URL that supplied bytes of the published file, in the order each first supplied one (an earlier process's included on a resume), and `url` is the first of them: one URL for a single-source download, `[]` and null for a file already in place and for a refusal.

### One process a source (`--manifest`)

Start-up, measured 2026-10-31 15:55 UTC (D03 T04 §23, medians of 20 runs each, `python3 -I`, the host at load 8 to 9 with Spark's evaluation and the lanes running): a bare interpreter 11.9 ms; `fetch.py` on its fetch path to a refused local connection (start, imports, arguments, the refused connect, its result line) 74.8 ms (minimum 69.8), so one process a file costs about 63 ms more than the interpreter alone. Of the imports, the modules a fetch needs (`http.client`, `ssl`, `hashlib`, `urllib.parse`, `socket`, `json`, `os`) take 45.7 ms against `pass`'s 14.4 ms in the same series; `argparse` would add 9.9 ms and `dataclasses` 9.8 ms, and neither is on the fetch path (`argparse` loads only for help or an error, `_quick_args`); `email.utils` adds 3.3 ms, since `http.client` loads most of `email` itself. So the lean import path is in place and deferring `email.utils` would save about 3 ms a process, while `--manifest` saves the whole 74.8 ms for every file of a source after its first (about 0.67 seconds for a source of ten files).

`python3 .fetch.py --manifest <file> [options]` downloads every file a source lists in one process (D03 T04 §23), several at once within the run's four connections, so the interpreter starts once a source instead of once a file. Each file is fetched exactly as its own run would fetch it: the same rules, state, resume, digest, refusals, per-source lock, source limit and free-space floor (counted over the source folder, so files already in place count against the limit for the next).

The manifest is JSON Lines, one object a file: `url`, `dest` (`<source>/<name>`), one of `sha256` or `md5`, an optional `mirrors` list of other URLs for that file, and optionally any of `source_limit`, `min_free`, `timeout`, `attempts`, `min_rate`, `segments` and `segment_threshold`. Precedence: a line's own value, then the command line's option, then the default. `--ca-file` and `--allow-loopback` hold for the whole run and are never read from a line; `--url`, `--dest`, `--sha256`, `--md5` and `--mirror` are refused beside `--manifest`. Blank lines are skipped.

Refused before anything is fetched (one message on standard error naming the line, nothing on standard output, exit 2): a manifest that cannot be read or lists no file; a line that is not a JSON object, has an unknown key or a value of the wrong type, lacks `url` or `dest`, has both digests or neither or one that is not hex of its length; a destination an earlier line named (however spelled: `src/a`, `src//a` and `./src/a` are one), or one that lands on a file another line's download writes while it works (its partial, state, state temporary or trial file; only the shared lock may be shared). A malformed URL is that file's own refusal line, not the manifest's, so a file already in place still reports `present`. Publication checks the file it renames into place is the one whose digest was verified, and refuses otherwise.

Results and exit: one JSON line a file, the same fields a single run prints, in the manifest's order (a file that finishes before an earlier one waits for that one's line). A failed file does not stop the ones after it. The exit is 0 only when every file is in place (`fetched` or `present`), 1 when any is not (its line says why: `refused` or `incomplete`), and 2 for a refused command line or manifest. Recovery: run the same command again. A file already in place and verified is reported `present` without a request, a partial resumes from its own state file, and the rest are fetched; a killed batch leaves the lines of the files it finished in order, and a rerun reports any later finished file `present`.

Connections: every request of every file in a batch, and every connection kept open between requests, holds one of the run's four places; files start in the manifest's order as places free up, a file takes a second place only when no file is waiting, and a large file's ranges split once places free. Where a source limit or the free-space floor binds, the earlier file in the manifest gets the room, as when files ran in turn. A range connection read whole and left open at the end of a file carries the next file's first requests to the same origin, as aria2c carries its connections from file to file; links to an origin the next file does not use are closed before it starts, and at most four are kept. Without the carry, a host that keeps each answer open until the pace of its last piece is paid saw the next file's `HEAD` and first range beside the last file's ranges: five open at once, measured on the bench. A single run keeps nothing.

Measured 2026-10-31 (the `batch` scenario of `scripts/glimmer/fetch_bench.py`, run alone through its own functions, 20 alternating pairs; the full bench's `batch` row is the record once it is run): 8 files of 4 MiB, each its own seeded payload and SHA-256, over HTTPS with 20 ms before every answer and 8 MiB/s per connection, four connections at most for each tool. `fetch.py --manifest` before files ran at once (four segments a file, one file after another, connections carried) took a median of 1.72 seconds; aria2c 1.37.0 with `--input-file` and `-j4 -x1 -s1` (four files at once, one connection each) 1.12; paired ratio 1.540, 95 percent interval 1.514 to 1.577: not met. Every run of both tools was whole, nothing refetched, four requests open at most at the host.
