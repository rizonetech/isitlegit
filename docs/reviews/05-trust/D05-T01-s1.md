1. **P1, lines 56–59: Alert delivery has no registered recipient, and verification does not establish outbound eligibility.** D05 T02 §4 and D05 T04 §5 consume the identity’s registered alert address, but this schema supplies only a finance contact. Moreover, `src/mail/allowlist.ts` refuses verification mail to verified non-demo addresses. Define and persist the alert recipient, or explicitly define its reuse of the finance contact; distinguish address verification from event-time mail eligibility. Test recipient read-back and the refusal for a verified but ineligible contact.

2. **P1, lines 57–59: Protection can survive removal of its prerequisites.** Existing delete routes in `src/auth/domains.ts` remove verified domains and addresses without consulting identities. After activation, deleting the last domain or finance address leaves the stored protected switch on and permits name-based discovery. Define effective protection after these removals, enforce it in registry reads and contact resolution, and test activation followed by each removal.

3. **P1, lines 54 and 60: Logo replacement ordering can leave a broken reference.** Writing the new extension, deleting the old extension, then failing the D1 update leaves the identity pointing at a deleted object. Same-extension replacement overwrites the existing logo before metadata and audit persistence succeed. Specify a replacement protocol that preserves the current object until the new reference commits, handles concurrent uploads and cleanup failures, and tests R2 and D1 failures at each transition.

4. **P1, lines 57–60: The tenant and private-data boundaries are unspecified and untested.** The proposed helpers accept an organisation ID, but the section does not establish whether callers must supply an authenticated tenant context or whether these are privileged internal helpers. The cross-organisation finance-contact test does not prove isolation of identity reads, updates or logo writes. Define that boundary and the minimal internal claim-match result; add two-organisation tests proving isolation and that private registry fields cannot enter checker-facing results.

5. **P2, lines 57–61: Reverse operations lack a complete persistence contract.** There is no logo-removal operation, and no tests for removing a display name, replacing existing identity fields, or switching protection off. Add these operations and read-back tests, including disappearance of removed names from matching, exclusion after unprotecting, logo-reference clearing before object deletion, and corresponding audit events.

6. **P2, lines 54, 60 and 64: The logo tests can pass with unusable images.** PNG signature and IHDR checks alone admit truncated files that cannot render. The hostile-SVG assertion also passes if sanitisation removes all meaningful artwork. Specify malformed-image and claimed-type mismatch refusals, require a usable image after sanitisation, and test valid PNG/SVG round-trips with meaningful content preserved. Include height-limit and failed-upload assertions proving the previous logo remains intact.

7. **P2, line 57: Matching and validation are insufficiently proven.** The stated tests can pass without case, whitespace or punctuation normalisation, and without rejecting unknown fields, empty names or excessive names. Define handling of names that normalise to empty and duplicate normalised names. Add positive normalisation cases, unrelated-name/domain negatives, schema-boundary tests, and persistence read-back. Otherwise a partial matcher satisfies every listed matching assertion.

8. **P2, lines 53, 56 and 61: Schema and audit acceptance tests prove only the happy path.** Creating one row in each table does not prove any CHECK or foreign-key constraint. Reading an event after a successful change does not prove the change and audit event commit together. Specify required nullability, JSON shape and logo-key/media-type consistency; test invalid writes and nonexistent organisations. Require atomic identity-change/audit persistence and inject an audit failure to prove rollback.
