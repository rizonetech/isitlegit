1. **P1, lines 194 and 212:** Widening the existing `verify` mail kind also widens permission for closed-loop bank-verification mail, which uses that same kind. A pending address claim would allow that unrelated mail outside the demo recipients permitted by spec §11. Add a distinct ownership-verification purpose, preserve the closed-loop restriction, and test both purposes against the same pending recipient.

2. **P1, lines 208, 210 and 211:** Code delivery has no failure or recovery contract. `sendMail` can return `failed`, `refused`, `uncertain`, or an unsuccessful `duplicate`; the section could report success for all of them and pass its checkpoint. Specify outcome handling, retry-safe send keys and recovery responses. Add an explicit sending-address resend operation, including expiry and lock recovery, and test it through Worker HTTP with stubbed delivery failures.

3. **P1, lines 207, 208 and 217:** Checking that members receive 403 does not prove organisation isolation. `requireOrg` supplies the active organisation but does not scope the new claim queries. Require organisation-scoped reads and mutations, and tests where another organisation’s owner tries to read, check, send a code for, verify and delete a claim. Assert unchanged persisted state and no mail attempt on refusal.

4. **P2, lines 207, 210 and 211:** The challenge lifecycle is incomplete. The section does not define whether resending invalidates previous codes, whether resending preserves an active lock, or whether successful verification consumes the challenge. Define these transitions, bind challenges to their claim and organisation, and test old-code rejection, resend during lock, successful consumption and concurrent attempts against the three-try limit.

5. **P2, lines 208 and 213:** Removal lacks a complete reverse-path contract. “Unverifies it” does not specify invalidating outstanding codes and DNS tokens, preventing an in-flight check from restoring verification, or what happens when a verified address and domain overlap. Define removal and re-addition semantics, including fresh proof and the surviving admission route, then test deletion followed by stale verification and sender lookup.

6. **P2, lines 208 and 217:** The route proof can pass with an empty list endpoint and mutation handlers that only enforce roles. Require owner/admin success tests that create claims, read back their TXT instructions and state, verify them, read back verification, remove them and confirm their absence or removed state. Define validation, missing-claim, claim-limit and ownership-conflict responses so §7 can render actionable errors. Test two pending organisations competing to verify the same domain or address.

7. **P2, line 209:** DNS checking specifies only matching, wrong-token and unreachable responses. It leaves ordinary propagation and provider-error states undefined: no TXT answer, NXDOMAIN, SERVFAIL, HTTP failure, malformed JSON and a request that never completes. Add a bounded timeout and distinct retryable-provider versus pending-proof outcomes, preserve pending state, and test these using representative DoH responses.

8. **P2, lines 194, 208 and 211:** The correction claims organisation claims and code sends are bounded, but the checklist explicitly caps pending domain claims and domain-code sends only. Sending-address claims have neither an explicit pending-claim cap nor the five-codes-per-hour requirement. Apply and test both bounds for addresses, including repeated claim requests and delete/recreate attempts; §6’s later per-address/IP limits do not establish these organisation-level bounds.

9. **P2, lines 204 and 217:** Build-order step 3 requires an email-handler test owned by the unbuilt D01 T01 §3, while the checkpoint explicitly defers that test. Replace this section’s acceptance condition with direct `findMemberBySender` tests against persisted claims and retain the named downstream handler test as D01 T01 §3’s obligation.
