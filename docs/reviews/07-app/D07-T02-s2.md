The software authenticator must respect credential discovery, otherwise manually supplying its saved credential ID conceals this failure.

Add those completion requests and assert refusal with no credential persisted. Otherwise the options endpoint can remain protected while the endpoint that actually saves the credential loses its guard, and every prescribed test still passes.

3. **P2, line 103: the migration generator’s new behaviour lacks executable proof.** Checking that committed migrations leave no missing schema does not test incremental generation, preservation of applied migrations, or the promised no-op. A broken generator can pass once `0008_auth_passkey.sql` exists. **Part 2: excellence**

Comparison: **Google Account passkeys**, as a leading authentication experience, not a phishing-checker competitor. Google documents device-unlock verification, passkey-first sign-in, another-device support, fallback and passkey removal. Its documented creation flow has two “Create a passkey” selections followed by device unlock; sign-in offers username entry or passkey selection followed by verification. These are documented flows, not timings measured in this review. [Google Account Help](https://support.google.com/accounts/answer/13548313?hl=en)

1. **out-of-scope: weaker verification default.** IsItLegit explicitly prefers user verification, and the plugin verifies with `requireUserVerification: false`; the software authenticator always sets the verified-user flag, hiding this distinction. Google describes sign-in as proving both device access and ability to unlock it. **Target:** require verified-user assertions and test rejection when the flag is absent. This needs a contract change first because `preferred` is explicitly decided, then implementation in D07 T02 §2. Evidence: [schema.ts:25](../../../src/auth/schema.ts#L25), [plugin:486](../../../node_modules/@better-auth/passkey/dist/index.mjs#L486), [webauthn.ts:140](../../../test/auth/webauthn.ts#L140). This does not negate the existing origin-based phishing resistance.

2. **out-of-scope: no delivered common-case advantage in steps or speed.** Google provides a usable browser flow; this candidate provides APIs. **Target:** one “Sign in with a passkey” activation plus authenticator approval, no email entry, and automatic return to the requested page. Measure post-approval navigation on a mid-range phone and South African mobile connection, with a proposed p95 target of two seconds. Ownership: **D07 T02 §7**. No comparative latency claim is currently supported.

3. **out-of-scope: recovery, accessibility and feedback have no delivered user-facing proof.** Google documents alternative sign-in and cleanup of credentials left in a password manager. IsItLegit’s deferred pages cannot yet demonstrate equivalent recovery or accessible operation. **Target:** cancellation returns to an actionable state immediately; email fallback takes one action; uncertain saves reconcile without duplicate enrollment; every operation works by keyboard and screen reader at 200% zoom, with announced progress/errors and no motion dependency. Ownership: **D07 T02 §7 and D07 T08 §3**. These are acceptance targets, not measured Google accessibility shortcomings.
