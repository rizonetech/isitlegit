1. **P1, lines 208, 220, 231: the required member view cannot use the specified reader.** `domainRoutes` applies its owner/admin gate to GET as well as mutations (`src/auth/domains.ts:489`). Calling it with a member’s cookie returns 403 instead of both read-only tables. Add an authorised read contract, coordinated with the app lane, or a scoped page reader. Test a real member session through the mounted page and database.

2. **P1, lines 208, 221, 229: audited removal depends on behaviour the API does not provide.** The domain and address DELETE handlers delete records without recording an audit event. Reusing them cannot satisfy “the audited removal”, while the section prohibits editing their owning module. Add an explicitly owned prerequisite for audited mutations, including the event contract, and prove the persisted event after a page-driven removal.

3. **P2, lines 229–230: removal consequences are incomplete and sometimes incorrect.** Removing the last verified domain or the verified finance-contact address disables Protected identity (`src/trust/identity.ts`). Conversely, removing a domain does not stop mail from independently verified addresses under it; removing an address does not stop mail admitted by its verified domain. Require confirmations that describe the actual consequences, and tests that read back both effective protection and sender eligibility after removal.

4. **P2, lines 228–230, 233–238: mutation failures lack a recovery contract and proof.** The plan specifies successful redirects and selected add refusals, but not a DELETE returning 404 after another tab removes the claim, an API/database outage, or session expiry during submission. Define the rendered outcome, preserved input and safe retry/navigation for each. Exercise these through form submissions and assert that failed mutations never display success.

5. **P2, lines 224–225: verification-method text can report false evidence.** Domain verification accepts codes sent to either `admin@` or `postmaster@`, but the plan always renders “A code mailed to admin@”. The domain list does not return the recipient. Use accurate recipient-neutral wording or add an owned reader for the recorded recipient; test a domain verified through `postmaster@`.

6. **P2, lines 223, 236: the empty-state contract contradicts the explicit deferral.** It requires “the two actions”, although Add a single address has no working destination until §27. Specify the interim empty state with only working actions and assign the second action’s addition to §27. Test every rendered empty-state action through its destination.
