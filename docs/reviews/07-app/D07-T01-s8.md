**Part 2: excellence**

Comparison: **Microsoft Fluent 2**, a strong shared-component alternative consistent with the manifesto’s Microsoft benchmark. Its documented system supplies explicit typography roles, contextual progress feedback and announcement behaviour for important messages. This comparison uses published guidance, not a measured Defender deployment. Sources: [Typography](https://fluent2.microsoft.design/typography), [Wait UX](https://fluent2.microsoft.design/wait-ux), [Message bar](https://fluent2.microsoft.design/components/web/react/core/messagebar/usage).

1. **in-scope, G1: Typography consistency falls short.** Fluent specifies complete type roles; this candidate substitutes one weight and inherited body spacing for several approved roles. Target: first-run heading 28px/1.2 at weight 800; error heading 32px/1.2 at weight 800; filtered heading 20px/1.3 and partial heading 16px/1.4 at weight 700; prescribed tracking throughout. Add computed-style assertions and inspect against the approved boards without introducing a pixel-difference gate.

2. **out-of-scope, G8: Accessible completion feedback is not delivered.** Fluent’s wait guidance explicitly includes state-change announcements. Here, `LoadingState` is live, but `PartialNotice` is a static `role="note"`; no delivered consumer establishes how a running report announces completion, partial results or failure. Target for D07 T03 §4: announce each meaningful transition once, announce the terminal outcome by the next two-second poll, preserve keyboard focus and avoid repeated announcements on unchanged polls. Verify with a screen reader and transition regression tests. This extends G4’s integration acceptance criteria; it does not require changing the approved visual surface.

There is insufficient runtime evidence to establish a speed, click-count or crash-recovery advantage or disadvantage. The component fixtures cannot substantiate those comparisons.
