1. **P1, [line 243](../../../todo/01-intake/TODO-01-email-intake.md#L243): Embedded messages are deliberately discarded on a false premise.** In version 1.29.0, `getAttachment()` exports embedded messages as `.msg` bytes ([implementation](../../../node_modules/@kenjiuno/msgreader/lib/MsgReader.js#L483)). Counting them in `omitted` also violates that field’s downstream contract: D02 T01 §1 describes omitted *body parts* and only emits its item when `truncated` is nonempty. An ordinary message containing another Outlook message can therefore lose the attachment without any disclosure. Require extraction and storage of the embedded message, with a fixture proving the stored bytes reopen with the expected contents.

2. **P2, [line 243](../../../todo/01-intake/TODO-01-email-intake.md#L243): Inline-image identity is missing from the mapping and proof.** Filename, media type and bytes do not preserve `ParsedAttachment.contentId`. Microsoft defines [PidTagAttachContentId](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagattachcontentid-canonical-property) as the connection between an attachment and its HTML `cid:` reference. D03 T02 §1 requires that connection to render images. Add explicit content-ID and disposition mapping, plus a twin fixture containing an inline image; read back the stored summary and image to prove the reference resolves.

3. **P2, [line 242](../../../todo/01-intake/TODO-01-email-intake.md#L242): The corrected header state has no complete production handoff.** `parseMsg(bytes)` cannot update a case itself. §7 currently writes `extractOriginal`’s optimistic header state before parsing, while `storeParsed` copies `forward.headersAvailable`, ignoring any additional property on `ParsedMessage`. Assign §7 the explicit responsibility to apply the parser’s result to both the case and the `Forward` passed to storage. Require a draft-message integration test reading back both D1 and `parsed.json`, including a failed update preventing checks.

4. **P2, [line 243](../../../todo/01-intake/TODO-01-email-intake.md#L243): HTML decoding is underspecified.** The library exposes both string `bodyHtml` and binary `html`; Microsoft specifies that binary HTML uses [PidTagInternetCodepage](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxcmail/59290e68-5bc7-4a2c-9824-846db0f365bc). A fixture covering only one representation can pass while ordinary Outlook HTML disappears or non-ASCII content is corrupted. Specify representation selection, charset handling and the charset retained for truncated bytes. Test binary HTML with a non-UTF-8 code page and verify both decoded content and stored overflow read-back.

5. **P2, [line 243](../../../todo/01-intake/TODO-01-email-intake.md#L243): Compressed-RTF bodies have neither support nor an explicit incomplete-content outcome.** Outlook clients can supply [only the compressed RTF body](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/supporting-formatted-text-in-outgoing-messages-client-responsibilities). Reading only text and HTML can therefore turn a populated message into a successful empty parse. Add bounded RTF handling, or explicitly detect unsupported body content and route it to §7’s partial outcome. Require an RTF-only fixture that cannot pass as an empty successful message.

6. **P2, [lines 244 and 247](../../../todo/01-intake/TODO-01-email-intake.md#L244): The unreadable-file refusal is asserted but untested.** `msgreader.getFileData()` can return `{ dataType: null, error: ... }` instead of throwing ([implementation](../../../node_modules/@kenjiuno/msgreader/lib/MsgReader.js#L458)). All specified checkpoint cases can pass while that result becomes an empty successful parse. Require tests for non-MSG bytes renamed `.msg`, a truncated compound file and the library’s returned-error outcome, each producing `ParseError` without writing a successful parsed summary.
