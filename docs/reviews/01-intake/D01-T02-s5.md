6. **missing-in-scope: reliable handoff when the operator alert is itself uncertain.** An alert timeout creates an uncertain `unresolved:*` row. Such rows are excluded from reconciliation, and the next attempt returns `duplicate` with `previous: uncertain`, which is nevertheless counted as `handedOver`. The operator can receive nothing indefinitely. Evidence: [src/mail/reconcile.ts:91](../../../src/mail/reconcile.ts#L91), [src/mail/reconcile.ts:146](../../../src/mail/reconcile.ts#L146). The synthetic probe reproduced false handoff success. Required test: alert timeout followed by repeated cron runs must remain visibly unresolved and support recovery without duplicate mail or recursive alerts.

7. **missing-in-scope: attempt-bound, repeat-safe manual resolution.** The CLI updates any `pending` or `uncertain` row without checking which attempt the operator inspected. Sequence: operator marks an old attempt failed, a caller starts another attempt, operator repeats the command after an ambiguous terminal result. The new pending attempt becomes failed and another caller can send again. Evidence: [scripts/mail-settle.ts:17](../../../scripts/mail-settle.ts#L17). An in-memory SQLite probe reproduced this transition. Require an expected attempt identity and refusal of an active/newer attempt; test the complete interleaving.

8. **missing-in-scope: malformed activity responses must fail safely.** `events: [null]` throws outside the request catch and aborts the run. A matching header without `email_id` or event type is accepted as a processed send with no provider ID. Both were reproduced with synthetic responses. Evidence: [src/mail/reconcile.ts:62](../../../src/mail/reconcile.ts#L62). Require validated event records, no settlement from incomplete evidence, and tests showing malformed responses cannot prevent subsequent eligible work.

9. **missing-in-scope: preserve the send log’s address-free contract.** Bounce reasons are copied into `mail_sends.error`; SMTP rejection text can contain the recipient address. A synthetic `550 user@example.com unknown` was stored unchanged. 10. **missing-in-scope: observable disabled and failed runs.** Missing credentials silently return `null`; search failures and missing operator configuration populate a report that the scheduled entrypoint discards. A revoked activity-search permission can therefore produce apparently successful cron executions without reconciliation. Evidence: [src/index.ts:19](../../../src/index.ts#L19), `src/index.ts:24`, `src/mail/reconcile.ts:101`, `:127`. Require secret-free operational failure/degraded signals and tests for missing configuration, permission rejection and exhausted lookup budgets.

**Part 2: excellence**

The strongest directly comparable alternative is **Resend’s provider-native idempotency**. Its documented behavior lets a caller repeat the same request within 24 hours and receive the original response without another send. Concurrent requests receive a retryable conflict. This is a documented comparison, not a measured latency benchmark. [Resend documentation](https://resend.com/docs/dashboard/emails/idempotency-keys)

1. **out-of-scope: recovery latency and operator effort.** This candidate first checks after 30 minutes, so normal cron alignment gives roughly 30 to 45 minutes before the first attempt. Unresolved cases wait three days, then require at least a provider lookup and a settlement command. Resend supports automatic replay within its retention window, with zero operator actions for that recovery path. **Target:** recover transient ambiguous submissions automatically within 60 seconds of provider recovery, with zero operator actions and zero duplicate sends. This needs a provider/dispatch design decision in **01-intake**, preserving the current prohibition on blind SMTP2GO retries.

2. **in-scope: backlog processing repeatedly wastes its lookup budget.** Each row starts again at page one, with no saved progress or shared window results. A match beyond page five can remain unreachable on every run; many uncertain rows also generate repeated searches without pacing against SMTP2GO’s documented 60-request-per-minute limit. Evidence: `src/mail/reconcile.ts:47`, `:89`, `:100`. **Target:** a six-page fixture reaches its last-page match across bounded runs; a 100-row fixture makes forward progress while respecting 60 requests per minute. Preserve conservative uncertainty when evidence is incomplete. [SMTP2GO activity reference](https://developers.smtp2go.com/reference/search-activity)

3. **in-scope: recovery feedback can claim success without evidence.** The uncertain-alert handoff and discarded failure reports in Part 1 leave the operator with less dependable feedback than an explicit replay result or conflict. **Target:** zero `handedOver` outcomes for uncertain alerts, and one inspectable, secret-free run outcome distinguishing settled, unresolved, degraded and disabled states. Cover these states through the actual scheduled entrypoint.
