1. **P1, [line 275](../../../todo/01-intake/TODO-01-email-intake.md#L275): `done` is committed before `reply` can fail.** The existing lifecycle forbids `done → partial`, so an exhausted reply failure cannot satisfy line 276. A failure recording the store step’s end event has the same problem. Move successful terminalisation after reply and its required recording. Add failure tests for `store` and `reply`, asserting the persisted status and failed-step event, not just the thrown error.

2. **P1, [lines 271 and 279](../../../todo/01-intake/TODO-01-email-intake.md#L271): startup and replay are not safe.** After an engine restart, repeating `setStatus(running)` against an already-running case returns `transition`; after the planned store finishes, the fresh `done` check skips the unfinished reply. Cloudflare can repeat code outside durable steps. Require checkpointed admission decisions, an idempotent running transition, and replay tests interrupted after that transition and between store and reply. A second invocation on an already-completed case proves neither recovery path. [Cloudflare Workflow rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)

3. **P1, [lines 276–278](../../../todo/01-intake/TODO-01-email-intake.md#L276): partial cases have no complete handoff to reply.** Catching a parse/checks failure and marking `partial` does not specify reaching `reply` with a usable report state. Parse failure can leave both verdict and parsed summary absent. D01 T02 §3 only specifies building a verdict reply; it does not fill this gap. Define the partial-state contract and route failures through the no-mail reply stub now. Test its failed-step payload without either missing artefact, and explicitly assign partial-message rendering to D01 T02 §3.

4. **P1, [lines 270–276](../../../todo/01-intake/TODO-01-email-intake.md#L270): typed database refusals can bypass retry and failure handling.** Only `setHeadersAvailable` explicitly requires checking its result. Case lookup, status changes and `recordEvent` also return failures as values, so a catch alone cannot detect them. Specify handling every result, distinguish missing cases from unavailable D1, and make failure-status/event persistence durably retryable. Inject failures into lookup, startup, event recording, verdict persistence and partial finalisation; verify recovery leaves the required rows and never falsely completes.

5. **P2, [line 276](../../../todo/01-intake/TODO-01-email-intake.md#L276): the retry checkpoint contradicts the configuration.** `limit: 3` means four total attempts. Three failures followed by success must recover, not finish partial. Specify the required retry delay, then test fourth-attempt recovery, four-attempt exhaustion and one-attempt `ParseError`. Exercise the configured Workflow binding, including its step sequence and retry configuration; typechecking or a callback-only `step.do` substitute cannot prove these behaviours. [Cloudflare retry semantics](https://developers.cloudflare.com/workflows/build/sleeping-and-retrying/)

6. **P2, [line 272](../../../todo/01-intake/TODO-01-email-intake.md#L272): parse wiring can be wrong while its checkpoint passes.** The assertions primarily prove header flags. An implementation that parses the outer forward instead of the extracted original can satisfy the `.eml` assertions. Include a storage failure followed by retry to prove this integration preserves the existing parser/store guarantees.

7. **P2, [line 275](../../../todo/01-intake/TODO-01-email-intake.md#L275): the new verdict store has incomplete deletion and persistence proof.** Explicitly require `ON DELETE CASCADE`; otherwise the specified foreign key blocks the case deletion on which D07 T02 §9 relies.
