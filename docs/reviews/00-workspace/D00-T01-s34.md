1. **P1: Pause does not address an already queued resume.** [§34, line 1145](../../../todo/00-workspace/TODO-01-repo-and-scaffold.md#L1145) requires a durable pause, but the heartbeat can enqueue before Interrupt records it. That pending message could subsequently resume the stopped session. Specify cancellation or invalidation of outstanding wakes, a generation check before continuation, and tests for pause during queue submission, after acceptance and before delivery. Explicit conversational stops also need a defined durable pause path, rather than assuming every stop produces Interrupt.

2. **P1: Active-state detection and event ordering are unspecified.** [Design, lines 5-7](../../specs/2026-11-04-codex-continuation-design.md#L5) names Stop and Interrupt but does not define how a new user turn marks an idle owner active. A heartbeat could resume a session already working, or a delayed Stop could overwrite a newer pause. Add the authoritative activity signal, ordered transition rules, and concurrency tests covering user turns, Stop, Interrupt and heartbeat dispatch. Atomic file writes alone do not establish event ordering.

3. **P1: Registration does not enforce exclusive writer ownership.** [§34, lines 1144-1147](../../../todo/00-workspace/TODO-01-repo-and-scaffold.md#L1144) binds an owner and checks tooling, but does not require the launcher and queued resume to share an exclusive execution claim. Two launches can pass readiness before either activates; rejecting one later hook does not stop that writer. Define acquisition before writing, concurrent-launch refusal, process-death recovery and explicit ownership transfer without clearing a stop. Test competing launches and heartbeat versus manual resume.

4. **P2: Queue acknowledgement and recovery lack a complete contract.** [Design, line 7](../../specs/2026-11-04-codex-continuation-design.md#L7) acknowledges on “the next matching lifecycle event” without defining correlation to the queued wake. An unrelated event could acknowledge it; an accepted but undelivered wake could suppress recovery indefinitely. Specify wake identity, acknowledgement evidence, deadlines, bounded recovery and ambiguous submission outcomes, including a crash after acceptance but before persistence. Test each transition and persisted read-back.

5. **P1: Blocked and completed work have no complete wake policy.** [Design, line 5](../../specs/2026-11-04-codex-continuation-design.md#L5) leaves non-`none` waits for “later inspection,” while [§34, line 1148](../../../todo/00-workspace/TODO-01-repo-and-scaffold.md#L1148) only requires a blocked-wait test. Specify who reevaluates stamp, coordinator-gate and time waits, when cleared waits wake once, how operator waits remain parked, and how completion disables continuation. Include missing/stale outboxes and tests proving both eventual wake and no endless resume after completion.

6. **P1: Completion can pass with runtime readiness still unproven.** [§34, line 1149](../../../todo/00-workspace/TODO-01-repo-and-scaffold.md#L1149) requires truthful records and explicit limitations, which can pass with no trusted hook execution or actual resumed session. Require separate acceptance evidence for each intended coordinator/lane session: trusted Stop execution, Interrupt pause, observed timer execution and acknowledged resume. Missing operator-controlled trust must leave runtime delivery incomplete while other work continues. Add timer restart/reboot and rollback verification without treating unit tests as installation evidence.
