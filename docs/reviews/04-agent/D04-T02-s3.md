1. **P1, lines 119–120: The 60-second limit is not a wall-time limit.** Checking time when `execute` starts permits a navigation, screenshot or other pending operation to continue past the deadline. The browser also remains active while §4 waits for the model. Add an independent deadline beginning at `open`, cancellation of pending browser work, and terminal closure without requiring another action. Test stalled opening, an action crossing the deadline, and expiry while no action is submitted.

2. **P1, lines 116–119: DNS validation is not bound to the browser’s connection.** The plan checks cached DoH answers, then lets Chrome resolve and connect independently. A hostile hostname can return a public address to validation and a private address to Chrome. Require enforcement at the connection-owning layer, or verified provider enforcement with equivalent local containment, and a test where validation and connection resolutions differ. Checking DNS alone does not establish the promised destination restriction. [OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

3. **P1, lines 119, 122, 124: Containment covers one page, but the promise covers the browser.** A lure can open a new tab or popup; the section neither refuses that target before its first request nor transfers it into the guarded walkthrough. It also leaves worker-originated traffic unspecified. Add a policy for additional targets and service workers, enforced before network activity, and close all walk-owned targets at termination. Test a `target="_blank"` lure and `window.open` to a prohibited destination, including their initial requests. Puppeteer exposes popups separately and has a separate service-worker bypass control. [Page events](https://pptr.dev/api/puppeteer.pageevent), [service-worker control](https://pptr.dev/api/puppeteer.page.setbypassserviceworker)

4. **P1, lines 119, 122: Request interception cannot prove the required non-HTTP navigation refusal.** In particular, a `javascript:` link executes script rather than issuing an HTTP request; checking `allowedUrl` in a request handler does not stop or log it. The specified `javascript:alert(1)` test can leave the URL unchanged while still executing the forbidden action. Add enforcement for non-network navigation paths and assert that script side effects never occur, alongside the refusal log. [JavaScript URL behaviour](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/javascript)

5. **P1, line 123: Screenshot persistence does not match the existing artefact contract.** The specified `walkthrough/<caseId>/<walkId>/<seq>.png` layout bypasses the `art/<caseId>/...` layout in `src/intake/store.ts`; the checklist requires an action row and R2 object but never explicitly requires the `artefacts` row consumed by `readArtefact` and the report route. Its test could pass while every report screenshot is unavailable, and prefix-based orphan cleanup misses these objects. Require the existing artefact writer and returned key, or explicitly extend all affected storage/read/deletion contracts. Prove read-back through the existing artefact reader and case cleanup.

6. **P2, lines 113, 118, 120–123: The audit schema cannot represent all required outcomes.** `seq` is restricted to 1 through 8, but the ninth attempted action must be stopped and logged after those eight rows exist. Initial-navigation refusals and background requests also have no defined action owner. Add a separate event sequence or walk-level terminal/request events, preserving the eight-executed-action limit. Test eight successful actions followed by a persisted ninth-attempt refusal without overwriting history, plus a blocked initial navigation.

7. **P2, lines 119, 121, 123: Validation failures have contradictory handling and unsafe logging is unspecified.** The zod allowlist rejects `Control+V` before normal execution, yet the section requires a logged `refused` result. Specify how malformed and unknown actions become bounded refusal records without browser interaction. Define safe serialization of `action_json`: storing rejected `type.text` verbatim could persist private text supplied by an injected model instruction, and storing accepted password text reverses §2’s hash-only persistence decision. Test refusal read-back and absence of submitted credential text in persisted records.

8. **P2, lines 119, 123–124: Failure cleanup and session release are unproven.** The required test observes only page closure, which can pass while the Browser Run session remains allocated. Cleanup explicitly covers Puppeteer errors but does not cover R2/D1 failures, interception-handler failures or partially completed `open`. Define terminal error results or typed exceptions, cleanup ownership, and retry behaviour after partial persistence. Inject these failures and assert session release, no further browser actions, and no successful result with missing evidence.

9. **P2, lines 112, 119, 127: The positive action tests can pass on a screenshot-only stub.** Receiving a PNG after each action proves neither clicking, typing, scrolling nor keyboard behaviour. Require observable page effects for every action type: click/double-click counters, pointer position, field value, focus or key effect, scroll offset and bounded elapsed wait. Also assert that screenshots reflect the resulting page state. The limit-removal checkpoint does not substitute for these functional assertions.

10. **P3, lines 112–127: Competitive superiority has no measurable comparison.** Microsoft Defender Safe Links, named by the manifesto’s benchmark family, is a strong relevant alternative with URL scanning and time-of-click verification; its documentation does not establish equivalent canary-driven walkthrough behaviour. Add a named benchmark owned by D08’s evaluation work, with §3 supplying measured completion time, refusal outcomes and usable screenshot traces for representative lure flows. Otherwise the plan cannot substantiate where this investigation beats that alternative. [Microsoft Safe Links](https://learn.microsoft.com/en-us/microsoft-365/security/office-365-security/safe-links?view=o365-worldwide)

This is a read-only source review of the exact candidate. The 21 passing tests, ten mutations, typecheck and lint results are supplied evidence, not checks I reran.

**Part 1: completeness**

1. **present: validated action interface.** All eight action types have bounded arguments and strict schemas. Evidence: [driver.ts:54](../../../src/walkthrough/driver.ts#L54); `driver.test.ts:150` tests rejected arguments, and lines 184 and 210 test browser effects. This section has no user interface, so menus, tooltips, command palettes and application shortcuts do not apply.

2. **present: consumed defaults and basic termination.** The driver reads the eight-attempt and 60-second defaults, counts refused attempts, starts its timer during opening and exposes `close()`. Evidence: `driver.ts:119`, `:295`, `:426`; `driver.test.ts:225` and `:242`. There is no user setting to persist.

3. **present: HTTP request policy.** Scheme, port, credentials, local names, literal addresses and resolved private addresses are checked; redirects return through interception. Evidence: [url-policy.ts:122](../../../src/walkthrough/url-policy.ts#L122), `driver.ts:212`; `url-policy.test.ts` and `driver.test.ts:295`. This establishes source and local-test coverage, not independent proof of production network isolation.

4. **present: canary-only typing.** Exact canary matching precedes typing; audit summaries omit typed text. Evidence: `driver.ts:334`, `:446`; `driver.test.ts:262`.

5. **missing-in-scope: navigation protection for keyboard activation.** The non-HTTP guard runs only for `click` and `double_click`; allowed `Tab` and `Enter` actions go directly to the browser. A page can focus a `javascript:` link, then the model can activate it with Enter without passing the guard that rejects the same link when clicked. Evidence: [driver.ts:334](../../../src/walkthrough/driver.ts#L334), `:366`; the existing test at `driver.test.ts:280` covers mouse activation only. Add regression coverage for focused links and keyboard form submission.

6. **missing-in-scope: browser-level download denial.** Download refusal depends exclusively on an intercepted response carrying `Content-Disposition: attachment`. A same-origin `<a download>` response without that header, or a page-generated Blob download, does not meet this condition. The driver does not configure browser-level download denial or audit download events. Evidence: [driver.ts:232](../../../src/walkthrough/driver.ts#L232); `driver.test.ts:295` tests only the attachment-header case. Prove that these other download paths are denied and recorded.

7. **missing-in-scope: closing worker targets.** The contract says workers and service workers are closed. `contain()` closes popup pages but merely records other target types. A hostile page's Blob worker can execute without fetching a worker script, so refusing network requests does not implement worker closure. Evidence: [driver.ts:254](../../../src/walkthrough/driver.ts#L254). Test a Blob worker and verify that it is stopped, not merely logged.

8. **missing-in-scope: durable request and interrupted-action auditing.** Ordinary request refusals only append to `blocked`; they do not create the promised `request` rows. `execute()` clears that array before each action, so refusals during initial loading or between actions disappear. An action interrupted by the wall clock likewise returns without an action row. Evidence: [driver.ts:172](../../../src/walkthrough/driver.ts#L172), `:309`, `:324`. Persist each refusal and each attempted action, including an explicit reason when a screenshot cannot be captured. Test initial-load, between-action and timeout cases by reading D1 back.

9. **missing-in-scope: consistent storage-failure cleanup and deadline results.** Malformed-action logging happens outside the failure handler: a D1 failure rejects `execute()` instead of returning `error` and closing immediately. Successful-action logging is also outside the deadline race; if that write finishes after the timer closes the browser, the method can still return `done`. Evidence: [driver.ts:301](../../../src/walkthrough/driver.ts#L301), `:321`. Test malformed input during D1 failure and a delayed audit write crossing the deadline. Neither should escape the declared result contract or report late success.

10. **present: screenshot persistence and read-back.** Screenshots use the existing artefact writer; action rows reference their keys. Tests read the stored bytes back. Evidence: `driver.ts:375`, [store.ts:241](../../../src/intake/store.ts#L241), `driver.test.ts:202`. R2 and D1 are the relevant storage systems; local temp-file replacement, locked files and local disk dialogs are not applicable.

11. **present: case-owned audit lifecycle.** Audit rows reference cases with `ON DELETE CASCADE`; screenshots use case-owned artefact paths. Evidence: [0050_walkthrough_actions.sql:7](../../../src/db/migrations/0050_walkthrough_actions.sql#L7), `driver.ts:377`. Browser actions against a remote site are not undoable transactions; this feature needs containment and case retention/deletion, not an Undo command.

Existing owners are D04 T02 §§4, 5 and 6, plus D07 T03 §13.
