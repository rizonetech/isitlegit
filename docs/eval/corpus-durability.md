# Generated PDF corpus storage contract

D08 T02 §19 owns publication and recovery in `eval/forensics/build.ts`. It does not regenerate the committed corpus, change its measurements, or reinterpret the process-termination evidence in §18. The plan self-review on `eb2dd3a8d` identified an inadequate survival oracle; the corrected contract requires persisted survival before regeneration and reserves refusal for unrecoverable starting states or failed storage assumptions.

## Supported storage assumptions

The offline builder requires Linux (including the Linux filesystem inside WSL), util-linux `flock`, one local filesystem for staging/live/backup/archive paths, atomic same-filesystem rename, and successful file and directory `fsync` that actually persist the requested data and namespace. The filesystem, kernel, storage controller and hardware must honor those requests. External fixture inputs must already be durably stored and remain unchanged during a build. They are not owned by the generated corpus transaction; a subsequent intentional fixture change is allowed and is verified against the next generated manifest.

Network filesystems, Windows/DrvFS, FUSE implementations without equivalent semantics, dishonest device flush acknowledgments, media corruption after synchronization, and physical power-loss behavior have not been validated. No hardware guarantee is claimed. A directory-open, synchronization or close error propagates as failure; there is no best-effort downgrade to process-only safety. An interrupted first build with no prior corpus need not produce a generation. Once a valid prior generation exists durably, interruption must leave it or the fully persisted new generation recoverable. A successful return requires the new generation itself to be persisted.

The lock serializes cooperating builders, including the legacy builder's lock during relocation. It does not coordinate arbitrary external editors. Existing SIGKILL tests prove process-termination recovery while OS caches survive. They do not prove machine-crash durability.

## Persistence boundaries

1. Establish directory ancestry: synchronize the publication parent and every ancestor through the filesystem root. This persists names created by recursive directory creation, including directories created by an earlier interrupted invocation.
2. Validate recovery candidates: parse both live and saved manifests and verify every generation-owned PDF hash and header. External fixture changes do not invalidate these saved owned bytes. A live generation is preferred only after validation. An invalid live generation with a valid saved generation is archived before the saved generation is restored. Both invalid generations cause refusal without deleting either.
3. Establish a durable prior generation: synchronize its files, then its directory, then parent ancestry. Invalid saved/live evidence is synchronized and moved into a unique `.pdf-forensics-damaged-*/generation` archive. Persist the archive directory and its ancestry before the move, then the destination and source parents after the move. No automatic archive cleanup runs.
4. Prepare the new generation: generate into a unique stage and validate all entries against their actual bytes, including current external fixtures. Synchronize all staged files, then the stage directory, then the publication parent. File data must precede persisted names.
5. Save the old generation: only after the live generation is verified and synchronized, remove a superseded valid backup and synchronize the parent. Rename live to backup and synchronize the parent before promotion. Invalid backups are archived, never silently deleted.
6. Publish: rename the synchronized stage to live, synchronize the parent, then validate the published manifest against current inputs. Return success only after these operations succeed. Failed promotion restores a verified backup. A synchronization error preserves evidence and is returned even when recovery succeeds; a valid promoted generation is not deleted merely because an error was reported.

Legacy relocation synchronizes each source tree and its ancestry, establishes archive ancestry, then persists both rename parents. It preserves original manifest paths and bytes. Stages abandoned after synchronization starts are retained for diagnosis, never selected as successful corpora merely by pathname. Ordinary generation/validation failures before synchronization remove only their own newly created stage. This deliberately trades bounded per-failure disk growth for preserved recovery evidence; archive removal is a separate explicit maintenance action.

## Falsifiable evidence and limits

`test/node/eval-forensics-durability.test.ts` runs the actual builder against a storage model with independent file-inode bytes and per-directory name maps. Only an intercepted `fsync` commits that object's current state into the model. Each mutation and synchronization boundary records a durable image. Restart materializes that image, discarding unsynchronized file data and namespace changes, before calling the real recovery code. The oracle first inspects persisted hashes without any generation, then aborts at the first generation write to ensure regeneration cannot mask lost bytes. Old and new manifests are deliberately distinct.

Mutation cases omit each of the six PDF synchronizations, the manifest synchronization, the stage directory synchronization, the final publication-parent synchronization, and each newly created ancestor synchronization. Each omission must lose the acknowledged new generation under the model. Other synchronizations conservatively establish prior durability or intermediate recovery boundaries and can be redundant for a particular already-durable starting image; the tests do not falsely claim every repeated `fsync` is individually necessary in every scenario. Recovery images include damaged live bytes and an intact backup. Synchronization failures are injected at every observed synchronization in a successful replacement and must propagate while retaining the previous verified generation.

The model tests loss of all unsynchronized state at every observed operation boundary, plus separate early writeback schedules that persist directory names without file bytes and file bytes without directory names. It is not an exhaustive filesystem simulator, torn-sector test, hardware experiment or proof across every possible writeback interleaving. Directory rename atomicity, correct flush semantics and already-durable external inputs are explicit assumptions. The documented guarantee is conditional on these assumptions, not a claim that SIGKILL emulates a power cut.
