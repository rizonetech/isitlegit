# Closed-loop verification request integration

Status: isolated service candidate for D05 T03 §1, 2026-11-04. Not shipped or stamped. Plan self-review and dispositions: `docs/reviews/05-trust/D05-T03-s1.md`. Coordinator assigned migration 0093 and this service to console; checks owns workflow, scheduled caller, evidence producer registry and atomic publication support/tests. Integration is mandatory before completion.

`requestVerification(deps, caseId, orgId)` from `src/trust/verify-request.ts` takes `{ db, mail: Omit<MailDeps, "db">, secret: string | undefined, now?: () => Date }`. Pass the existing `BETTER_AUTH_SECRET` as `secret` and SMTP2GO dependencies through `mail`. The service uses no model or live transport in tests. The returned `VerificationResult` contains only `{ outcome: "none" | "requested" | "unavailable", evidence: EvidenceDraft[] }`; no reply token, contact address, signing secret or registered bank fragment may enter a Workflow step result or logs.

The queued caller must execute after invoice rules are persisted, for both forwarded mail and standalone documents, before the verdict consumes evidence. The service reads the current case owner and current-run critical `invoice.bank_changed` registry mismatch, verifies the attachment belongs to that case, requires a complete invoice amount/currency/last-three snapshot, and refuses ambiguous multiple invoices. It rechecks actual `closed-loop` entitlement and the protected supplier's verified finance contact immediately before calling the mail layer. The mail layer enforces its existing demo-only `verify` allowlist.

Migration `src/db/migrations/0093_verifications.sql` pins one immutable request per case. Full HMAC-SHA-256 under a versioned domain separator binds all context, a nonce, recipient hash and expiry. Base64url encoding gives a 43-character token and a 50-character Reply-To local part. Only transient mail construction and outbound Reply-To contain that token. Retry uses the stored winner's context, refuses changes or expiry, and reconstructs the same token. Mail send key `verification:<caseId>` preserves existing sent/failed/uncertain/refused claims and retry semantics. The request expires 72 hours after creation; mail states that fixed deadline in SAST, including retries. `sent_at` records first observed confirmation, not a claimed provider acceptance timestamp.

`requested` returns info `verification.requested` with the invoice-owned `amount_cents`, `currency`, `account_last3`, `attachment`, `source_evidence`, supplier organisation ID, expiry and delivery confirmation time. `unavailable` returns info `verification.not_requested` with a bounded reason code. Its wording says delivery could not be confirmed, including uncertainty, rather than asserting nothing was sent. Neither path changes the existing critical invoice evidence or severity floor. `none` has no drafts. Storage failures throw; callers must not turn them into silent success.

The checks caller must admit `verification` as a later producer and publish through validated `addEvidence`. Do not rename these drafts to `invoice.*` or relax the evidence schema. The integration checkpoint is `test/pipeline/verification-request.test.ts` plus the isolated service tests. It must prove real queued invocation, execution-time entitlement lapse, tenant isolation, safe durable results/logs and truthful failure handling.

`refreshVerificationDeliveries(db, { limit })`, where limit is an integer from 1 through 25, returns `{ caseId, orgId, runId, evidence }[]` for confirmed mail needing evidence publication, without sending mail. Checks calls it after `reconcileUncertain`. Candidates are restricted to the same current run and no answer; scanned stale rows rotate behind other candidates. Failed publication stays eligible until `acknowledgeVerificationDelivery(db, caseId, runId)` succeeds after publication.

Publication must atomically guard the exact current run, owner and unanswered request, including the evidence deletion and insertion. An asynchronous preflight followed by unguarded replacement is insufficient: a case rerun or §2 reply can race it. Checks owns the minimal evidence-store guard and adversarial integration proof; the service alone does not provide that atomic guard. ACK only a successful publication, never a skipped or failed one. Preserve `verification.answered` if a reply wins. Console will wait for this integration before its single implementation round and final completion review.

Reply routing, authenticated sender/token/expiry checks and answer handling remain D05 T03 §2. This service does not claim that replies are handled yet.
