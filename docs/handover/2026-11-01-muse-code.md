## 4. How the process works (repository tooling, model-neutral)

All of this lives in the repository and works whichever agent runs it.

- The plan: `todo/` (TODO files with sections and checklists), `todo/implementation-plan.md` (generated), `todo/lanes.json` (who owns what). Workflow: `docs/todo-workflow.md` and `todo/README.md`.
- `python3 scripts/todo-graph.py`: `validate`, `resolve <ref>`, `query ready|blocked --all`, `plan --sync`, `stamp`, `plan-candidate`. A section is done only when `stamp` writes its receipt; `stamp` refuses without the plan review, completion review and clean rounds.
- Reviews: `python3 scripts/review-dispatch.py --writer <claude|codex|gemini> --kind plan|completion` (rounds without `--kind`). `.conclave/reviewers.toml` routes each writer to a reviewer of another model family (claude and gemini to Astra via Codex, codex to Argon via Antigravity) and holds the schedule (efforts at most medium). **Muse Code needs its own route**: add `muse = ["astra"]` (or another family) under `[routes]` and a matching `--writer muse` in the dispatcher's writer list before its first review; ask the operator which reviewer.
- Run a review in the background and wait for it (never `--timeout`; reviews take 5 to 25 minutes).
- Git hooks (`scripts/hooks/`, installed by `pnpm install`): pre-commit runs `plan --sync` and graph checks; pre-push runs typecheck and lint on the exact HEAD and refuses a dirty tree.
- `scripts/campaign_guard.py`: the run guard each lane's long run held (`acquire`, `stop-hook`); see its docstring.
- CI (`.github/workflows/ci.yml`): Worker tests in 4 shards, Chromium tests in their own project and 3 serial shards (`vitest.config.ts` finds them by import), gates; lane branches cancel superseded runs, `main` and `coordinator-gate` never do.

## 5. The coordinator's job (now Muse Code's)

- Merge a lane's head only when nothing unstamped (product code) sits beneath it; offline tooling, tests and docs may come unstamped. Regenerate generated files on conflict, never pick a side: `pnpm build:css && node scripts/hash-asset.ts` (assets), `pnpm types` (Worker types).
- Gate: push to `coordinator-gate`, wait for every CI job green, then move `main` from a clean detached worktree (`git worktree add --detach <dir> <sha>`, `pnpm install --frozen-lockfile`, `git push origin HEAD:refs/heads/main`).
- Deploy (from that worktree, `docs/operations.md`): `pnpm exec wrangler d1 migrations list DB --remote`; read each pending migration for DROP TABLE and check nothing references the table; count rows before; `pnpm db:migrate:remote`; confirm "No migrations to apply"; count rows after; `pnpm exec wrangler deploy --var COMMIT_SHA:<sha>`; `/health` must report the sha; `node scripts/smoke.ts https://isitlegit.derick-f5a.workers.dev --commit <sha>` with `OP_SERVICE_ACCOUNT_TOKEN` from `~/.conclave/secrets/op-service-account-token.env`; record the row in `docs/coordinator.md` Deploys.
- Migration numbers: only the coordinator assigns them, in the ledger, before a lane writes one.
- Watch CI on every branch (`gh run list --status completed`, `gh run view <id> --log-failed`), and send each red to its owner with the failing test; fix shared tooling yourself with a regression test.

## 6. Claude Code features used, and what Muse Code needs instead

| Claude Code feature | What it did here | Muse Code (from its public docs; verify before relying on it) |
| --- | --- | --- |
| One session per lane in a git worktree | parallel lanes | separate Muse Code sessions, one per worktree |
| Cross-session messages (`SendMessage` over local Unix sockets) | coordinator and lanes talked: stamps, approvals, migration numbers | Muse Code sessions message each other over a local Unix socket ([Meta for Developers](https://developer.meta.com/ai/resources/blog/muse-code-new-plans-and-features/)) |
| Scheduled prompts (`CronCreate`: lane heartbeats, the coordinator's hourly check) | lanes woke to merge `main` and resume; hourly health and CI sweep | no scheduled tasks documented; use Muse Code's background agents ([Verdent](https://www.verdent.ai/guides/agents/what-is-muse-code)), or a systemd user timer that starts a headless run |
| `Monitor` (5-minute CI watch) and background commands | the coordinator heard every red and gate result | background agents, or a timer script around `gh run list` |
| Skills in `.claude/skills/` (process-plan, process-phase, process-todo-section, review-todo-section, add-todo, create-todo, groom-plan, independent-review, local-tool-safety, process-todo-file, authoring-skills) | the section workflow | Muse Code has skills and can import Claude skills ([termic](https://github.com/simion/termic/releases/tag/v1.2.3)); without them, follow `docs/todo-workflow.md` |
| Project hooks (`.claude/settings.json`): `scripts/dispatch_hook.py` before Bash (reviews only in the background), `campaign_guard.py stop-hook` | enforcement | no hooks documented; the git hooks and CI still enforce the plan, the stamp and the gates |
| Global hooks (`~/.claude/hooks/`): layer rules, superpowers block | writing and fix-at-the-layer rules | carry the rules in `AGENTS.md` (already there) |
| Persistent memory (`~/.claude/projects/.../memory/`) | operator rules between sessions | the rules that matter are in `AGENTS.md` and `docs/coordinator.md`; section 7 repeats the essentials |
| `AskUserQuestion` | operator decisions, recorded with time in `docs/coordinator.md` | ask in the session; keep recording each decision there |
| Subagents | rarely, read-only help | Muse Code subagents and Workflow ([Meta Research](https://research.meta.ai/blog/introducing-muse-code-and-muse-spark-1-2)) |

Muse Code is new (launch-era beta per third-party write-ups); test each of these before a long unattended run.
