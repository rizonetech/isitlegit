# TODO workflow

Installed by the Conclave-SDK `todo` kit. Link this file from the project's `AGENTS.md` (for example: "Plan and build through the TODO system in [docs/todo-workflow.md](./docs/todo-workflow.md).") so every agent reads it.

`todo/` is the live execution plan; format spec: `todo/README.md`. Markdown is canonical.

Core mechanics: the Implementation Order table in each TODO file is the dependency graph; a row flips to `[x]` only through `python scripts/todo-graph.py stamp`, backed by a review receipt in `docs/reviews/`; `todo/implementation-plan.md` is regenerated by `plan --sync`, never ticked or edited by hand; cross-references (`§N`, `TNN §N`, `DNN TNN §N`) are bidirectional; every section declares Phase, Needs and Surface, carries a Build order with `Done when:` per step, and must be implementable with zero conversation context.

Granularity and 100% plan completeness:
- **Small, single-responsibility sections:** Never bundle multiple subsystems, dialogs, or workflows into one coarse umbrella section. Split every TODO file into small, single-responsibility sections that each deliver one coherent, testable capability.
- **Short table descriptions (`<= 88` chars):** Keep section headings (`## N. <Title>`), `Deliverable` cells in `Implementation Order`, and `Scope` cells in index tables to a concise noun phrase of at most 88 characters so raw Markdown table rows stay under 140 characters (with description cells <= 88 characters) and never wrap in raw `.md` editors. Put file paths, symbols, CLI flags, and enumerations in the section body and micro-steps, never in the heading or table cell.
- **Granular micro-step checklist items:** Every section carries 1 to 30 buildable micro-step items (typically 4 to 15 concrete micro-steps, never a 1-bullet summary stub), ending with `- [ ] Commit: <message>`. Each non-Commit item names one action, a concrete path/symbol/command in backticks, an observable `Done when:` in the same bullet, a `Cheaper substitute:` on UI and write items, and a source citation when copying behavior from the plan or SPEC.
- **100% complete development plan:** Running `process-plan` to completion must produce a 100% complete, shippable product with zero unowned surfaces, controls, settings, refusal/error paths, undo/reverse paths, or persistence read-backs. Never cap operator-requested planning and never silently drop scope.

For TODO work, use the skill in your agent's isolated skill directory (`.agents/skills/`, `.claude/skills/`, or `.codex/skills/`) that owns the step: capture through `add-todo`, author a file through `create-todo`, build through `process-todo-section`, stamp through `review-todo-section`, close a file through `process-todo-file`, run a phase or the plan through `process-phase` or `process-plan`, harden the tree through `groom-plan`. The lifecycle is: capture, author, validate, record `Started:`, implement, run the section's gates, commit, review and stamp, sync the plan.

## Rules for TODO work

- **Plan before build:** a section's plan review reads the commit that records its `Started:` line or an earlier one, or a later commit only when the section has an explicit `Started:` line and, every commit that descends from the Started commit and leads to the candidate (a branch forked after it included) changes only `todo/` and `docs/reviews/`, or reformats an existing JSON file under `test/` or `tests/` to the same parsed value, and leaves the section's contract (its text and its TODO file's preamble, its own Implementation Order row found by its `§N` column) byte for byte as it was; the receipt records that evidence as `plan.after_started` and validation rebuilds it, and refuses it missing when the candidate follows the Started commit (D00 T01 §28).
- **Tests prove claims:** a section's Test checkpoint must be able to fail, and is quoted, not paraphrased, in its stamp.
- **Commits:** trunk-based `main`, concise imperative messages, the section ref in the body. Commits follow logical steps within a section; review fix-loop commits append to the candidate range. Never amend a candidate under review, never bypass hooks, never force-push.

```bash
python3 scripts/todo-graph.py plan --check    # generated plan is current (CI runs this)
python3 scripts/todo-graph.py query lane      # this checkout's lane and its domains (todo/lanes.json)
python3 scripts/todo-graph.py query ready     # dependency-safe work right now, this lane's rows
python3 scripts/todo-graph.py query blocked   # this lane's sections waiting, and on what
python3 scripts/todo-graph.py query stats     # this lane's tree health; --all the whole plan, --phase N one phase

python3 scripts/todo-graph.py query deferred  # open and resolved deferrals

```

Report only commands actually run, and distinguish static evidence, test output and review proof.

### Recover a returned combined result

The dispatcher writes pending-call identity under `build/review-completion/` before the normal combined call and durably retains the response before findings write. If that write fails, the returned result is unrecorded and cannot support a stamp. Recover the same persisted response without invoking a reviewer again:

```bash
python3 scripts/review-dispatch.py --recover-completion --record <findings-path>
```

An unresolved `calling` state or failed result persistence stays blocked for explicit recovery. Preserve the marker; never delete it to permit another call or assume no response returned. A recorded known outage with no returned review may retry through the dispatcher. Text and JSON `--list-rounds` expose pending and recorded state despite the historical command name.

## Recovering an interrupted stamp

If the process dies after writing its receipt but before updating the TODO, `validate` reports an orphan receipt. Preserve that receipt. Rerun the same `stamp` command with every original argument and the explicit original `--date YYYY-MM-DD` printed by the diagnostic, even when retrying on a later day. Recovery revalidates all review and safety evidence and requires identical receipt fields and JSON types; different formatting alone is allowed. It preserves the receipt bytes and refuses a different date, SHA, check, review or other field, naming the first difference. A failed recovery preserves the original receipt and restores the TODO and projection.

If the TODO already contains its Verified and Review metadata, do not stamp it again. Run `python3 scripts/todo-graph.py validate`, then `python3 scripts/todo-graph.py plan --sync` to repair the interrupted projection. These commands validate the real receipt; synchronization preserves the receipt and existing stamp metadata. Orphan diagnostics run only in explicit `validate`, so ordinary graph queries and the recovery stamp can still enter. Never delete or edit a receipt to force recovery.

Review journal publication on POSIX synchronizes the journal file and every ancestor directory, from its containing directory through the filesystem root, before returning. This includes directories created earlier by the section lock. A failed directory open or synchronization propagates and prevents a new reviewer invocation; existing uncertain markers, returned responses and retry archives remain evidence for supported recovery. Returned-response recovery never invokes another reviewer. Windows retains the existing file synchronization and atomic replacement behavior but skips directory synchronization; machine-crash durability of directory ancestry on Windows is not proven by these POSIX tests.
