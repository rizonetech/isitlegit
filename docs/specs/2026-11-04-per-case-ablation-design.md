## Wire contract

Agreed with eval in `eval-ablation-wire-agreed`, 4 November 2026. `POST /api/upload` accepts one file, one textual `replayRunId` and one textual `ablate` JSON object for an experimental upload. The object has exactly `experimentId`, `arm`, `manifestDigest` and `deployment`. `experimentId` and `replayRunId` match `^[A-Za-z0-9_-]{1,64}$`; `arm` is `full`, `no-agent-reasoning`, `no-walkthrough`, `no-sam`, `no-transcribe` or `no-screening`; digest is 64 lowercase hexadecimal characters and deployment is 40 lowercase hexadecimal characters equal to the running `COMMIT_SHA`. Unknown keys, malformed JSON, non-text, duplicate fields and ablate without replay identity are rejected before admission. Ordinary uploads and replay-only uploads retain their current contract.

The manifest digest is SHA-256 of UTF-8 `JSON.stringify({seed,sets,setVersions,deployment,ids})`, with those property positions, sets and IDs in manifest order, and setVersions keys inserted in sorted order. Mutable arm status/runId and experimentId are excluded. The runner owns computing and preserving it; the server binds the supplied digest immutably and does not claim to have received or independently validated the population itself.

Only a signed-in member of the exact configured `EVAL_ORG_ID` can submit any ablation metadata. A non-eval organisation gets 403; malformed fields get 400; a deployment or immutable identity conflict gets 409. These refusals create no case, file or Workflow. Existing daily limits, replay deduplication and model budget accounting still apply. No flag or experiment identity comes from a model or organisation-wide KV.

## Durable identity

Migration `0095_case_experiments.sql` adds three tables without rebuilding cases:

- `eval_experiments(org_id, experiment_id, manifest_digest, deployment)`: immutable manifest binding, primary key organisation and experiment ID.
- `eval_experiment_arms(org_id, experiment_id, arm, replay_run_id)`: one immutable replay ID per experiment/arm and one binding per organisation/replay ID.
- `case_experiments(case_id, org_id, experiment_id, arm, replay_run_id, upload_key, active_upload_key)`: one immutable attribution per case, foreign keys to its arm and case, and a unique organisation/replay/active-upload-key tuple. The active key equals upload_key until a definitively unstarted RawMissing admission releases it; original identity and upload_key never change. The upload key is the existing hash of bytes/name/media type, not raw content.

Deletion follows organisation/case retention through foreign keys. Updates cannot change identity. Only the active sample binding may change from its original key to null, in the same transaction that settles a definitively unstarted case as RawMissing; it can never be reactivated or changed to another key. The normal intake claim remains keyed by organisation, replay ID and upload content/name/type identity, so the same arm/sample retry returns the same case and different arm replay IDs produce fresh cases. A reused replay ID with different experiment, flag, digest or deployment is refused, not treated as a duplicate. While its case is retained, an experimental sample remains idempotent after the normal 24-hour intake claim expires, by its durable upload-key binding; ordinary replay expiry is unchanged. Conflicting concurrent reservations have one winner and one explicit conflict.

An R2 failure followed by definitive RawMissing settlement preserves the failed case and its immutable attribution but clears active_upload_key in that same settlement transaction. The same upload may then create a replacement case under the same experiment/arm; only that replacement becomes the active sample. Unknown storage/Workflow status retains the binding and requires recovery rather than an automatic new case. Existing RawMissing quota exclusion remains unchanged. Tests cover R2 failure, sweep and eventual same-upload retry execution.

Bind the experiment and arm before any case admission. Persist case attribution before storing its raw file and before starting its Workflow. If attribution persistence fails, no raw file is written and existing intake recovery settles the case as an incomplete admission. A stored file therefore implies durable experiment attribution; a sweep can start from case ID alone. Retry, sweep and Workflow resume never reread a caller-supplied or KV flag.

Both successful admission and duplicate responses include `experiment: {experimentId, arm, manifestDigest, deployment, replayRunId}` read from D1. Ordinary responses omit it. Eval's existing direct-D1 reader joins the three tables by organisation/experiment/arm and reads by case ID; another organisation cannot obtain this through the authenticated upload route. Read or schema failures are errors, never an unflagged experiment. A resumed experimental case on a different deployment cannot spend against an incomparable arm.

### Immutable registry and capture validation

Read only `eval/monitor-manifests/<manifestDigest>.json` from the existing artifact bucket. The strict bounded manifest has version1, kind monitor-screening, seed, deployment, modelVersions, settingsDigest and1to15 ordered pages. Each page is exactly `{experimentCaseId,pageId,captureDigest,labelDigest}`. IDs are unique within the manifest. Labels never reach the model; labelDigest binds the private frozen label/rubric, and the published registry attests approved provenance without exposing the label.

Canonical digest is lowercase SHA256 of UTF-8 ECMAScript JSON.stringify of exactly `{version:1,kind:"monitor-screening",seed,deployment,modelVersions,settingsDigest,pages}` in that top-level order. Insert modelVersions keys using Object.keys().sort()/Object.fromEntries(), retaining JavaScript enumeration semantics; preserve page order and each page's field order above. Preserve supplied Unicode and standard JSON escaping; no normalization, indentation, BOM or trailing newline. Runtime compares the digest, current deployment and exact model/settings fingerprint before execution. modelVersions names immutable Loupe model revision and Spark version (the actual source constants, not a mutable deployment nickname); settingsDigest binds the actual parking, input, fallback/second-look and request settings. Changes require a new manifest/experiment rather than mutable resume.

A capture digest addresses an immutable provenance manifest at `eval/monitor-captures/<captureDigest>.json`, with exact fields in this canonical JSON.stringify order: `{version:1,pageId,provenanceDigest,capturedAt,originalUrl,finalUrl,redirects,screenshotSha256,textSha256,signalsSha256}`. The digest hashes that exact projection. pageId matches the manifest; provenanceDigest is64 lowerhex referencing the coordinator-accepted source/provenance record, capturedAt is an ISO UTC timestamp, original/final URLs and up to8 redirect URLs are credential-free http(s) URLs of at most2048 characters. URL strings remain byte-exact, with no normalization. The published registry attests approval of the private provenance and label records; neither the consumer nor trigger invents that approval.

Object keys are derived solely from verified content hashes: `eval/monitor-objects/<screenshotSha256>.jpg`, `<textSha256>.txt` and `<signalsSha256>.json`. There are no caller-selected keys or network fetches for these captures. The screenshot is a whole JPEG, at most10MiB and32 million pixels; text is fatal-decoded UTF-8 of at most1MiB and200000 characters. The strict signals object is exactly `{text,inputs,passwords,forms,iframes,components,hidden}`, with text at most200000 characters and each count a nonnegative safe integer. Its byte limit is1MiB. Registry/experiment/capture JSON each has a64KiB limit. Hash bytes before interpreting them, compare every digest, reject malformed/oversized/extra/duplicate fields before any model call, and preserve the same frozen bytes for both arms. Population preflight validates pages sequentially and discards their large buffers; execution rereads and revalidates one page at a time, never holds15 screenshots in Worker memory. Private labels are absent from these model input objects. Root publication writes objects satisfying this consumer schema and owns approval/readback; product code reads only. A missing object/provenance, mismatched fingerprint or corrupt content is an explicit failure, never ordinary-mode fallback.

The exact modelVersions keys are loupe and spark: Loupe's immutable modelNameOf(DEPLOYED_VERSION), excluding its deployment suffix, and actual SPARK_MODEL (currently muse-spark-1.3). Compare against the source constants used by the real adapter, not a registry-provided override. The settings fingerprint is SHA256 of UTF-8 JSON.stringify in this exact order: `{version:1,deployment,mode:"image",maxPages:SCREEN_CALLS_PER_RUN,maxTextCharacters:MAX_TEXT_CHARACTERS,loupeMaxAnswerTokens:MAX_ANSWER_TOKENS,sparkMaxOutputTokens:SPARK_MAX_OUTPUT_TOKENS,sparkReasoningEffort:SPARK_REASONING_EFFORT,escalationBand:{low,high},parking:{maxText:PARKED_MAX_TEXT,emptyText:EMPTY_MAX_TEXT,emptyScreenshot:EMPTY_MAX_SCREENSHOT,maxHidden:MAX_HIDDEN_TEXT,imageLedText:IMAGE_LED_MAX_TEXT,imageLedScreenshot:IMAGE_LED_MIN_SCREENSHOT},secondLook:true}`. Values come from owning production constants. The deployment binds the actual parking patterns, prompt/schema and policy source as well; a changed source/settings/model/deployment cannot resume under the prior experiment. Readback reports actual invoked target revisions/call IDs, not an unsupported claim that a mutable remote deployment was independently remeasured.

No training copy, production alert, finding/takedown or capture-cache overwrite occurs.

Readback includes terminal/pending/error state, digests, actual revisions, screener/fallback and exercised reason, timing and spend/reservation linkage.
