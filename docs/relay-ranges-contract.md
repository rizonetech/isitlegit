# Configured relay lifecycle service contract

D02 T02 §10 owns `src/auth/relay-ranges.ts` and migration 0094. This contract is implementation input for console D07 T04 §37 and D07 T05 §6; it does not claim either surface or §11 trust consumption is implemented. The governing design is `docs/specs/2026-11-04-gateway-relay-ranges-design.md`.

## Authentication and request boundary

These exports are internal service functions, not HTTP handlers. Console must construct a `RelayPrincipal` exclusively from server-authenticated context: `{kind: "member", userId: signedIn.user.id, orgId: activeMembership.org.id}` or `{kind: "reviewer", accessEmail: c.get("accessEmail")}` after the existing `requireAccess` middleware succeeds. Never accept a principal, actor, role, organisation authority or verification flag from request JSON. Route CSRF/origin enforcement and Access signature/audience/issuer/expiry checks remain mandatory in the console-owned adapters. A member's selected organisation must come from the authenticated membership, not a submitted orgId. The service separately checks the current database membership role (owner/admin), open organisation and verified domain claim, including inside each mutation batch. A reviewer with any membership under its verified email in the target organisation is refused, regardless of the role or another active organisation.

`RelayDeps` takes `db`, optional DNS `resolve`, and optional `now`. Production uses the existing bounded DNS-over-HTTPS resolver and real clock. Tests supply synthetic DNS, never a production bypass for reserved ranges. No model, mail, tenant-supplied URL fetch or paid call occurs. Independent review is a human responsibility: the authenticated reviewer must check the official gateway source and subset relation before submitting approval. A URL/digest alone is not automatically verified by this service.

## Calls and results

All calls return `{ok: true, value}` or `{ok: false, kind}` with `invalid`, `forbidden`, `conflict` or `unavailable`. Never turn an unavailable result into an empty/default editable configuration. A successful mutation may also have `replayed: true`; that value is the immutable original operation outcome, so reload current state separately before presenting the current revision after a retry.

- `discoverRelayBindings(deps, member, {orgId, claimId})` discovers gateway/provider choices for one verified owned claim, with bounded DNS work and explicit failure. An empty success means no supported discovered gateway/provider. It does not create configuration or trust.
- `readRelayBinding(deps, principal, binding)` reads a single current configuration, revalidating the current DNS binding. `binding` is `{orgId, claimId, gateway, provider}`; gateway is the discovered wildcard pattern and provider is `microsoft` or `google`. A nonexistent configuration returns `automatic` with version 0. A changed binding returns conflict, not a trusted historical configuration.
- `mutateRelayBinding(deps, principal, action)` takes the binding plus `expectedVersion` and an 8 to 128 character `requestKey`. `propose` adds 1 to 64 public CIDRs; `approve` adds the exact `revision` and `source: {url, digest, retrievedAt}`; `reject` adds the exact revision and one of `source-unavailable`, `range-mismatch`, `binding-changed`; `revoke` and `restore` add no extra fields. Unknown fields are rejected. Approve/reject require a reviewer, the other actions require a member admin. Use the same key for an exact retry; changed payload or actor with an existing key conflicts.
- `pendingRelayBindings(deps, reviewer, {after?, limit?})` returns `{items, nextCursor}` using bounded keyset pagination (default 25, maximum 50). It excludes unverified/deleted claims, closed tenants and every tenant in which the reviewer has membership. Listing does not prove a current DNS binding; read and approve revalidate it.
- `relayBindingHistory(deps, principal, {...binding, after?, limit?})` returns bounded immutable operation outcomes for that binding with the same tenant and reviewer checks. It reads stored audit outcomes, not reconstructed current values.

A snapshot contains the binding, `version`, `revision`, `state`, canonical `cidrs`, `actor`, `updatedAt`, `source` and bounded `reason`. Version advances for each accepted operation; a proposal's revision identifies its immutable ranges. Approve/reject changes state for exactly the pending revision. Edit creates a new pending revision and immediately retires prior trust. Revoke leaves an explicit revoked hold; restore leaves a versioned automatic marker with no active revision and clears discovery cache. The versioned marker prevents stale editors from recreating an old override after removal. Every accepted operation persists one idempotent audit outcome and invalidates only its discovery-cache tuple in the same transaction. Revoke/restore can remove trust during DNS failure or a changed binding; they still require current tenant/claim authority. Claim or organisation deletion cascades configuration and its lifecycle records.

## Consumption boundary

§11 must treat pending/rejected/revoked snapshots as explicit holds, verified snapshots as exclusive current overrides, and automatic snapshots as requiring fresh DNS discovery after restoration. Configuration never populates `org_receiving_chains`. It must compare the version again at authentication-evidence persistence, fail closed on errors, and retain historical evidence provenance. This service alone does not activate configured relay trust.

## Validation provenance

CIDRs use strict canonical network parsing and reject host bits, zero prefix, mixed-family spelling, non-global and special-purpose address ranges. The IANA [IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/) and [IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/) registries were checked on 4 November 2026. This feature accepts ordinary global unicast allocations, excluding special-purpose allocations even when an individual special purpose has global reachability. Those allocations are not ordinary gateway egress. It neither infers provider ownership from a public address nor treats an accepted range as verified.
